# 迪米特原则案例教学：班级信息查询

## 一、面试回答：什么是迪米特原则？

迪米特原则（Law of Demeter，LoD）也常被称为**最少知识原则**。它要求一个对象只和“直接朋友”通信，对不需要了解的内部对象和内部结构保持无知。

通俗地说：**让对象只做好自己该知道的事，不要通过一个对象去操纵它内部的另一个对象。**

这里的“直接朋友”通常包括：

- 当前对象的成员变量；
- 方法参数；
- 方法内创建的对象；
- 当前对象自身。

它并不是机械地禁止调用 getter，而是避免出现“链式探查内部结构”的代码，例如：

```java
// 不推荐：校长知道教师持有学生列表，并亲自遍历学生计算成绩
double total = 0;
for (Student student : teacher.getStudentList()) {
    total += student.getGrade();
}
```

上述代码让 `Principal` 同时依赖 `Teacher`、`List<Student>` 和 `Student` 的成绩字段。一旦学生的保存方式、统计口径或成绩模型变化，校长相关代码也可能被迫修改。

更合适的做法是让拥有学生数据的 `Teacher` 提供业务语义明确的方法：

```java
// 推荐：校长只提出“需要什么”，教师负责“怎么得到”
double total = teacher.clazzTotalScore();
```

这样可以降低耦合、隐藏实现细节，也让职责更清晰。面试中还应补充：迪米特原则追求的是**适度封装**，不是把所有调用层层包装；过度应用会造成大量没有业务含义的转发方法。

## 二、工程结构与业务场景

本工程模拟“校长查询某班级信息”的场景：

| 类 | 扮演的角色 | 主要职责 |
| --- | --- | --- |
| `Student` | 学生实体 | 保存学生姓名、排名、成绩。 |
| `Teacher` | 班级数据的拥有者 | 保存学生集合，并计算班级人数、总分、平均分。 |
| `Principal` | 查询发起者 / 上层调用者 | 向教师获取班级汇总信息，组装为 `Map` 返回。 |
| `ApiTest` | 测试入口 | 调用 `Principal.queryClazzInfo`，将查询结果输出为 JSON。 |

调用关系如下：

```text
ApiTest
   │
   ▼
Principal ──请求汇总数据──► Teacher ──遍历内部学生──► Student
   │                            │
   └──── 组装班级、教师、人数、总分、平均分 ────┘
```

## 三、本案例如何体现迪米特原则

核心代码位于 `Principal.queryClazzInfo(String clazzId)`：

```java
int stuCount = teacher.clazzStudentCount();
double totalScore = teacher.clazzTotalScore();
double averageScore = teacher.clazzAverageScore();
```

### 1. `Principal` 只依赖直接朋友 `Teacher`

`Principal` 的成员变量是 `Teacher teacher`，因此 `Teacher` 是它的直接朋友。校长只调用教师公开的三个班级统计方法，以及教师自己的名称、班级信息；它不直接操作学生集合。

### 2. 学生集合的遍历被封装在 `Teacher` 内部

`Teacher.clazzTotalScore()` 与 `Teacher.clazzAverageScore()` 自己遍历 `studentList` 并读取 `Student.getGrade()`。对 `Teacher` 而言，学生是其直接管理的数据，统计逻辑放在这里符合“数据与行为靠近”的设计。

这使得 `Principal` 无需知道以下细节：

- 学生数据是 `List`、数据库查询结果还是远程接口结果；
- 总分、平均分具体如何计算；
- `Student` 中成绩字段的命名及其存取方式。

### 3. 变化被限制在合适的位置

若日后平均分需要排除缺考学生、成绩改为由其他对象计算，主要修改 `Teacher` 的统计实现即可；`Principal` 仍然调用 `clazzAverageScore()`，通常不受影响。这正是迪米特原则降低“变化传播范围”的价值。

## 四、与违反原则的写法对比

如果把 `Principal` 改成直接取得学生列表并计算：

```java
// 反例：Principal 认识了 Teacher 的内部协作者 Student
List<Student> students = Teacher.getStudentList();
double total = 0;
for (Student student : students) {
    total += student.getGrade();
}
```

那么校长既要负责管理层的查询，又要负责学生统计；而且它与 `Student`、集合类型和统计规则产生额外耦合。这种“通过朋友访问陌生人”的方式不利于维护。

当前工程用 `Teacher` 的 `clazzStudentCount()`、`clazzTotalScore()` 和 `clazzAverageScore()` 替代了这段逻辑，因此主调用路径遵循迪米特原则。

## 五、代码中的改进点

案例的主思路正确，但作为生产代码还可以继续收紧封装：

1. `Teacher.getStudentList()` 当前是 `public static`，会把可变的内部 `List<Student>` 直接暴露给外部，外部仍可绕过教师自行遍历甚至修改集合。这会削弱本案例的封装效果。若没有业务需求，应删除它；若需要只读查询，应返回不可修改的副本或只读视图，并优先提供有业务语义的查询方法。
2. `studentList` 也被声明为 `static`，意味着所有教师共享同一份学生列表。实际业务通常应将其改为实例字段，并通过构造器或仓储注入。
3. `queryClazzInfo(String clazzId)` 尚未使用传入的 `clazzId`，而教师和班级在字段初始化时被固定。真实系统中应据此查询对应教师/班级，或移除无效参数。
4. 返回 `Map<String, Object>` 便于演示，但字段类型和键名缺少编译期约束。业务系统更建议定义 `ClazzInfo` DTO。
5. 总分与平均分各自遍历一次学生列表；若一次请求同时需要两者，可在 `Teacher` 内部一次遍历完成统计，避免重复工作。

这些建议不是要求让 `Principal` 了解更多内部细节；相反，它们进一步保证由 `Teacher`（或专门的班级领域对象）持有数据与业务规则。

## 六、面试追问

### 1. 迪米特原则和封装有什么关系？

封装是隐藏对象的数据和实现；迪米特原则进一步约束对象之间的交互范围。封装强调“内部不要随意暴露”，迪米特原则强调“外部不要探查得太深”，两者共同降低耦合。

### 2. 迪米特原则是不是“不能调用 getter”？

不是。调用直接朋友的 getter 是允许的。需要警惕的是把 getter 当作穿透内部结构的通道，例如 `a.getB().getC().doSomething()`；这往往说明调用方知道了不该知道的对象关系。也要结合业务语义判断，不能为了规避链式调用而制造大量无意义的包装方法。

### 3. 本例中为什么统计方法应该放在 `Teacher`，而不是 `Principal`？

因为 `Teacher` 持有并管理班级学生数据，是最了解统计规则的对象。把行为放在数据附近，校长只关心查询结果，职责单一且对学生模型变化不敏感。

### 4. 迪米特原则和单一职责原则的区别是什么？

单一职责原则关注“一个类为什么变化”，避免职责过多；迪米特原则关注“对象知道谁、依赖谁”，避免对象之间交互过深。此例中，`Teacher` 负责统计而 `Principal` 负责查询编排，体现职责划分；校长不遍历学生，则体现最少知识。

### 5. 什么时候不应过度使用迪米特原则？

简单的数据传输、DTO 读取或性能敏感的热点路径中，额外的包装可能降低可读性或增加复杂度。应以清晰的领域边界和稳定的业务接口为准，而非为了形式上的“少调用”不断增加中间层。
