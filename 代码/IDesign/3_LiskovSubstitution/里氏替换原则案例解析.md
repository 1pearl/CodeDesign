# `3_LiskovSubstitution`：里氏替换原则案例解析

> 面向对象设计原则中的 LSP（Liskov Substitution Principle，里氏替换原则）可以先这样理解：
>
> **凡是使用父类对象的地方，都应该能够透明地换成其子类对象，并且程序仍然正确。**
>
> 子类对象应该能够替换父类对象，并且不会破坏原有程序的正确性。

这里的“正确”不只是“不报错”，还包括：调用方原本依赖的业务含义、返回结果和使用限制不能被悄悄破坏。

---

## 1. 这个工程模拟了什么

工程用三种银行卡来演示继承关系：

```text
BankCard（抽象的银行卡）
└── CashCard（储蓄卡/现金卡）
    └── CreditCard（信用卡）
```

对应的源码文件：

| 类 | 文件 | 在案例中的职责 |
| --- | --- | --- |
| `BankCard` | `src/main/java/com/ivanzhao/design/BankCard.java` | 定义所有银行卡都有的基础能力：入账、出账、查询流水。 |
| `CashCard` | `src/main/java/com/ivanzhao/design/CashCard.java` | 在基础银行卡上增加提现、储蓄（充值）、风控校验。 |
| `CreditCard` | `src/main/java/com/ivanzhao/design/CreditCard.java` | 在继承来的能力上增加贷款（`loan`）和还款（`repayment`）。 |
| `APITest` | `src/test/java/com/ivanzhao/design/test/APITest.java` | 演示把 `CreditCard` 当成 `CashCard` 来使用。 |

## 2. 先认识三个类

### 2.1 `BankCard`：共同的父类能力

`BankCard` 是抽象类，保存了每张卡共同的数据：

```java
private String cardNo;   // 卡号
private String cardDate; // 开卡时间
```

它还提供了两种公共操作：

```java
public String positive(String orderId, BigDecimal amount) // 正向入账
public String negative(String orderId, BigDecimal amount) // 逆向入账/出账
```

可以把它们暂时理解成银行系统底层的两条通用记账通道：

```text
positive(...)  入账：存钱、还款
negative(...)  出账：取现、放款
```

此外，`tradeFlow()` 用于查询交易流水。

`BankCard` 中还有一个包可见的抽象方法：

```java
abstract boolean rule(BigDecimal amount);
```

它表示“不同卡种可以有不同金额规则”，但本工程的公开交易流程**没有调用它**。因此它当前只是一个没有真正接入业务的扩展点。

### 2.2 `CashCard`：把通用记账封装成储蓄卡动作

`CashCard extends BankCard`，它实现了 `rule`：

```java
boolean rule(BigDecimal amount) {
    return true;
}
```

即样例里储蓄卡对金额不做限制。

它把父类的“记账术语”包装成用户看得懂的业务动作：

```java
public String withdrawal(...) { // 提现
    return super.negative(...); // 出账
}

public String recharge(...) {   // 储蓄/充值
    return super.positive(...); // 入账
}
```

还额外提供 `checkRisk(...)`，模拟风控检查。

### 2.3 `CreditCard`：在现有能力上增加信用卡特有操作

`CreditCard extends CashCard`。它没有重写 `withdrawal` 或 `recharge`，所以这两个方法原样继承自 `CashCard`。

它新增了：

```java
public String loan(...)      // 贷款/信用额度放款
public String repayment(...) // 还款
```

其中：

- `loan` 先用 `rule2` 限制金额不超过 1000，再调用 `super.negative(...)` 出账；
- `repayment` 调用 `super.positive(...)` 入账。

```java
boolean rule2(BigDecimal amount) {
    return amount.compareTo(new BigDecimal(1000)) <= 0;
}
```

## 3. 里氏替换在测试代码中的直接体现

最关键的代码位于 `APITest.test_bankCard()`：

```java
CashCard bankCard = new CashCard("6214567800989876", "2022-03-05");
bankCard.withdrawal("100001", new BigDecimal(100));
bankCard.recharge("100001", new BigDecimal(100));

CashCard creditCard = new CreditCard("6214567800989876", "2022-03-05");
creditCard.withdrawal("100001", new BigDecimal(1000000));
creditCard.recharge("100001", new BigDecimal(100));
```

第二段的左边是 `CashCard`，右边却创建了 `CreditCard`：

```java
CashCard creditCard = new CreditCard(...);
```

这正是“**用子类对象替换父类对象**”：

```text
原先：CashCard 类型变量 → 放入 CashCard 对象
替换：CashCard 类型变量 → 放入 CreditCard 对象
```

为什么能编译？因为 `CreditCard` 是 `CashCard` 的子类。Java 保证子类对象至少具备父类中可访问的方法，因此下面两句仍可调用：

```java
creditCard.withdrawal(...); // 来自 CashCard
creditCard.recharge(...);   // 来自 CashCard
```

这里可以把调用方想象为“ATM 服务”：它只要求拿到一张能 `withdrawal` 和 `recharge` 的 `CashCard`。如果给它一张 `CreditCard`，而信用卡也能按照相同约定完成这两个动作，那么 ATM 服务无需修改代码——这就是 LSP 希望达到的效果。

## 4. 这个案例满足 LSP 的地方

从**代码结构和测试所调用的方法**来看，这个示例的替换是成立的：

1. `CreditCard` 拥有 `CashCard` 的公开方法。
  
   `CreditCard` 继承了 `withdrawal`、`recharge`、`checkRisk`，因此原来针对 `CashCard` 的调用代码可以继续编译和运行。

2. `CreditCard` 没有削弱被测试的父类行为。
  
   它没有把 `withdrawal` 改成“永远失败”，也没有让 `recharge` 抛异常；继承的方法依然按原流程调用父类的出账或入账操作。

3. 子类只增加了能力。
  
   `loan` 与 `repayment` 是信用卡专有能力。它们不会影响一个只把对象当作 `CashCard` 使用的调用方。

因此，在案例限定的前提下，以下替换是安全的：

```text
需要 CashCard 的代码
        ↓
传入 CreditCard
        ↓
仍只调用 CashCard 已承诺的 withdrawal / recharge
        ↓
行为可继续完成
```

## 5. 初学者最容易误解的点

### 5.1 能赋值，不等于一定符合里氏替换原则

下面这句能够编译：

```java
CashCard creditCard = new CreditCard(...);
```

只说明 Java 的继承类型关系允许这样赋值；它是 LSP 的**必要基础**，但不是完整证明。

真正的 LSP 要继续问：把所有可能的 `CashCard` 换成 `CreditCard` 后，业务是否仍然符合调用方预期？

例如，假如后来把信用卡的 `withdrawal` 改为：

```java
@Override
public String withdrawal(String orderId, BigDecimal amount) {
    throw new UnsupportedOperationException("信用卡不能提现吗");
}
```

那么原先所有依赖 `CashCard.withdrawal` 的代码都会在替换后失败。虽然仍然“能赋值”，但已经违反 LSP。

### 5.2 本例的继承在真实业务中有语义风险

类图表达的是：

```text
CreditCard 是一种 CashCard
```

这在技术演示中是为了便于展示替换；但在真实银行领域，信用卡和储蓄卡通常是并列卡种：

- 储蓄卡的资金来自账户余额；
- 信用卡的可用资金来自授信额度，涉及账单、额度、利息等规则；
- “充值/储蓄”的含义和“信用卡还款”也不完全相同。

也就是说，若系统把 `CashCard` 的含义严格定义为“储蓄卡”，`CreditCard` 未必真的是一种 `CashCard`。此时 `CreditCard extends CashCard` 的“is-a（是一个）”关系就不够准确，业务上可能违反 LSP。

本代码中尤其可见两个信号：

- 测试让 `CreditCard` 调用继承来的 `withdrawal("100001", 1000000)`，但信用卡自身的 `loan` 又限定了不超过 1000；这两个“资金支出”入口的金额规则不一致。
- `CreditCard` 没有重写父类的 `rule`，而是另写了 `rule2`。由于 `withdrawal` 没有调用任何规则，信用卡从储蓄卡继承的提现操作绕开了 `rule2`。

因此应把本工程理解为：**它展示了 LSP 的语法形式和一个基本替换场景，但不是一个完全严谨的银行领域建模。**

## 6. 若要让设计更贴近 LSP，可怎样调整

更稳妥的做法是把“所有银行卡共有的能力”提升到共同抽象，而不要让信用卡继承“储蓄卡”。例如：

```text
BankCard（共同抽象）
├── CashCard（储蓄卡）
│   ├── withdrawal（提现）
│   └── recharge（存款）
└── CreditCard（信用卡）
    ├── loan（借款/消费）
    └── repayment（还款）
```

两类卡共同复用 `BankCard` 的入账、出账、流水能力；各自只暴露和自己业务语义相符的方法。这样调用方应依赖更合适的抽象，例如：

```java
BankCard card = ...;
card.tradeFlow();
```

而不是假定“任何信用卡都必须是储蓄卡”。

如果确实存在一个“可出账”的通用业务需求，还可以进一步抽取小接口：

```java
interface DebitOperation {
    String debit(String orderId, BigDecimal amount);
}
```

调用方依赖 `DebitOperation`，储蓄卡与信用卡都按各自规则实现它。这比用 `CreditCard extends CashCard` 更准确，也更容易保证替换后的规则一致。

## 7. 一句话总结

本项目通过 `CashCard creditCard = new CreditCard(...)` 展示了：**子类 `CreditCard` 可以在需要父类 `CashCard` 的位置被使用，且继承的提现、储蓄操作仍能工作。** 这就是里氏替换原则的直观形式。

但要牢记，LSP 关注的是“替换后业务契约仍成立”。在真实建模中，信用卡和储蓄卡更适合共同继承 `BankCard`，而不是让信用卡继承储蓄卡；否则不同的额度、资金和还款规则可能让这种替换失去业务正确性。

## 8. 原工程是否包含反例？

**不包含。** 原工程的 `CreditCard` 没有重写 `CashCard.withdrawal` 和 `CashCard.recharge`，因此测试中用 `CreditCard` 替代 `CashCard` 时，调用的仍是父类原有实现。它展示的是一个“表面上可替换、且所测行为没有被破坏”的正向例子。

原工程虽然存在前文提到的业务建模风险（例如信用卡继承储蓄卡），但它没有写出一个明确的、会让父类调用方失败的反例。所以本次在保留原有类不动的基础上，新增了以下两个文件：

| 文件 | 用途 |
| --- | --- |
| `src/main/java/com/ivanzhao/design/NoWithdrawalCreditCard.java` | 一个故意违反 LSP 的子类。 |
| `src/test/java/com/ivanzhao/design/test/LspViolationTest.java` | 用 JUnit 观察“能赋值、运行却失败”的替换结果。 |

## 9. 扩展反例：不能提现的信用卡错误继承储蓄卡

假设某种信用卡因业务规则**不允许提现**。开发者却仍让它继承 `CashCard`：

```java
public class NoWithdrawalCreditCard extends CashCard {

    public NoWithdrawalCreditCard(String cardNo, String cardDate) {
        super(cardNo, cardDate);
    }

    @Override
    public String withdrawal(String orderId, BigDecimal amount) {
        throw new UnsupportedOperationException("该信用卡不支持提现");
    }
}
```

从 Java 类型角度，它仍然是 `CashCard` 的子类，因此下面这句没有问题：

```java
CashCard card = new NoWithdrawalCreditCard("6214567800989876", "2022-03-05");
```

但一个依赖 `CashCard` 的调用方会合理地写出：

```java
card.withdrawal("100002", new BigDecimal("100"));
```

调用过程如下：

```text
调用方要求：一张 CashCard，且要执行提现
        ↓
传入：NoWithdrawalCreditCard（静态类型仍是 CashCard）
        ↓
Java 动态分派到子类重写的 withdrawal
        ↓
抛出 UnsupportedOperationException
        ↓
原先可工作的 CashCard 调用方失败
```

新增的 `LspViolationTest` 将这个预期异常写成测试断言：

```java
@Test(expected = UnsupportedOperationException.class)
public void noWithdrawalCreditCardCannotReplaceCashCard() {
    CashCard card = new NoWithdrawalCreditCard(...);
    card.withdrawal("100002", new BigDecimal("100"));
}
```

这里测试“通过”并不表示设计正确；恰恰相反，测试通过表示我们成功观察到预期的异常，证明该子类**不能**替代父类。

### 为什么这违反 LSP？

`CashCard` 的公共方法 `withdrawal` 已向使用者作出契约：给我合法订单号和金额，就能执行提现并返回状态码。原工程中它会继续调用 `negative`，最终返回成功码 `"0000"`。

`NoWithdrawalCreditCard` 的问题是它把父类本来支持的操作取消了：

- 父类允许提现；
- 子类拒绝提现并抛异常；
- 调用方不需要、也不应该在每次调用前先判断“这是不是特殊子类”。

这属于子类**削弱了父类已经承诺的能力**。替换后调用方的前置条件被变得更苛刻：以前只要传入任意 `CashCard` 就能提现，现在还必须额外保证“它不是 `NoWithdrawalCreditCard`”。因此违反 LSP。

### 错误修复方式与正确修复方式

不要通过类型判断来补洞：

```java
if (card instanceof NoWithdrawalCreditCard) {
    // 不提现
} else {
    card.withdrawal(orderId, amount);
}
```

这会让每个调用方都知道具体子类，新增卡种时还要反复修改，失去多态的价值。

应该修改抽象关系：让 `NoWithdrawalCreditCard` 不再继承 `CashCard`，而是与 `CashCard` 并列继承 `BankCard`；或者让“支持提现”成为一个单独的小接口，仅由真正支持提现的卡实现。

```text
BankCard
├── CashCard implements WithdrawalCapable
└── NoWithdrawalCreditCard
```

这样，提现服务只接收 `WithdrawalCapable`，不会误把不能提现的信用卡当作储蓄卡。

## 10. 面试官可能的追问与参考回答

### 追问 1：里氏替换原则的标准表述是什么？

**回答：** 如果 `S` 是 `T` 的子类型，那么所有使用 `T` 的地方都应能替换成 `S`，且不影响程序正确性。工程实践中可以理解为：子类要遵守父类对外暴露的方法契约，不能让调用方因为换了子类而改变原有用法。

### 追问 2：`CashCard card = new CreditCard(...)` 能编译，是否就说明符合 LSP？

**回答：** 不说明。这只证明 Java 的类型系统允许向上转型。LSP 还要求运行行为与业务语义不被破坏。例如 `NoWithdrawalCreditCard` 也能赋给 `CashCard` 变量，但调用 `withdrawal` 时会异常，所以不符合 LSP。

### 追问 3：子类新增方法会违反 LSP 吗？

**回答：** 通常不会。比如原工程的 `CreditCard` 新增 `loan`、`repayment`，只要它没有改变从 `CashCard` 继承的方法契约，使用 `CashCard` 的旧代码仍然可以正常工作。风险在于子类删除、拒绝或改变父类已有能力。

### 追问 4：子类返回不同的结果一定违反 LSP 吗？

**回答：** 不一定，关键看是否还在父类允许的契约范围内。父类如果承诺“返回成功或失败状态码”，子类因自身数据而返回失败码可能合理；但父类承诺能完成操作，子类却改为抛出调用方未预期的异常或完全不支持该操作，通常就是违约。

### 追问 5：子类能否增加校验、限制金额或抛出更多异常？

**回答：** 要非常谨慎。父类允许任意正金额提现，子类却规定“只允许 100 元以内”，等于提高了调用方必须满足的前置条件，旧调用方可能失败，通常违反 LSP。子类可以放宽父类可接受的输入条件，但不应收紧；异常也不应比父类契约更苛刻。

### 追问 6：本工程中 `CreditCard extends CashCard` 真的合理吗？

**回答：** 作为语法演示可以，因为它让 `CreditCard` 复用了 `withdrawal` 与 `recharge`；作为领域建模则值得质疑。信用卡通常不是一种储蓄卡，它们的资金来源、额度、还款和计费规则不同。更合理的模型通常是二者并列继承 `BankCard`，再按能力抽取接口。

### 追问 7：LSP 和“面向接口编程”有什么关系？

**回答：** LSP 说明“实现类/子类能否安全替换抽象”；面向接口编程则建议调用方依赖稳定、细小的抽象而非具体类。二者配合使用：先为真实能力设计接口，再确保每个实现都遵守接口契约，替换才会安全。

### 追问 8：如何在代码评审中发现 LSP 违反？

**回答：** 可重点检查子类是否重写父类方法后出现以下迹象：抛出 `UnsupportedOperationException`、返回值语义改变、参数限制变严格、可接受状态变少、需要调用方增加 `instanceof` 判断，或子类只是“为了复用代码”而继承了一个并不符合“是一个”关系的父类。
