# 接口隔离原则案例教学：英雄技能接口

## 一、什么是接口隔离原则？

接口隔离原则（Interface Segregation Principle，ISP）指：**客户端不应该被迫依赖它不需要的方法；一个类对另一个类的依赖，应建立在最小的必要接口上。**

通俗地说，不要设计一个“什么都能做”的大接口，再要求所有实现类把所有方法实现一遍；应该按调用方真正需要的能力，把接口拆成小而内聚的角色接口，让实现类按需组合。

接口隔离原则解决的核心问题是“接口污染”：当接口包含过多不相关的方法时，实现类即使没有该能力也必须实现它，通常只能留下空实现、抛出异常或写无意义代码。这样一来，接口一变更会牵连大量并不需要该功能的类。

例如，若把所有英雄技能都定义到一个接口中：

```java
interface ISkill {
    void doArchery();
    void doInvisible();
    void doSilent();
    void doVertigo();
}
```

只会射箭、隐身和沉默的英雄也不得不实现 `doVertigo()`；即使没有眩晕能力也要写一个空方法，这就是不符合 ISP 的信号。

更合理的方式是按能力拆分：

```java
interface ISkillArchery { void doArchery(); }
interface ISkillVertigo { void doVertigo(); }
```

英雄只实现自己具备的技能接口。调用方若只要“射箭”，也只依赖 `ISkillArchery`，而不依赖其他技能。

> ISP 的重点不是“接口的方法越少越好”，而是“接口要按稳定、内聚的客户端需求划分”。过度拆分会造成接口碎片化，反而增加理解和组合成本。

## 二、工程结构与对比关系

该工程通过两套包结构对比接口设计：

| 区域 | 设计目的 | 代表类 |
| --- | --- | --- |
| `com.ivanzhao.design.Common` | 未进行接口隔离的反例 | `ISkill`、`HeroHouYi`、`HeroLianPo` |
| `com.ivanzhao.design.ISP` | 应用接口隔离原则的正例 | 四个 `ISkillXxx` 接口及 `impl` 下英雄类 |
| `src/test/.../common` | 演示反例调用 | `common.ApiTest` |
| `src/test/.../ISP` | 演示正例调用 | `ISP.ApiTest` |

两种方案的差别如下：

```text
反例 Common：
HeroHouYi ─┐
HeroLianPo ├── implements ISkill（射箭、隐身、沉默、眩晕）
           ┘        ↑ 每个英雄都被迫依赖全部技能

正例 ISP：
HeroHouYi  ── implements ── ISkillArchery + ISkillInvisible + ISkillSilent
HeroLianPo ── implements ── ISkillInvisible + ISkillSilent + ISkillVertigo
                              ↑ 每个英雄只依赖自己拥有的技能
```

## 三、哪里没有体现接口隔离原则：`Common` 包

### 1. `ISkill` 是一个臃肿接口

`Common/ISkill.java` 同时声明了射箭、隐身、沉默、眩晕四种技能。它把不同英雄可选的能力捆绑成了一个强制合同，所有实现者都必须依赖全部四个方法。

### 2. 英雄类出现无意义的空实现

`Common/HeroHouYi.java` 中：

```java
@Override
public void doVertigo() {
    // 无此技能的实现
}
```

后羿没有眩晕能力，却因为实现 `ISkill` 被迫实现 `doVertigo()`。同样，`Common/HeroLianPo.java` 中的 `doArchery()` 是空实现，廉颇被迫依赖自己不具备的射箭能力。

空实现会制造错误的类型承诺：从 `ISkill` 类型看，调用方会认为任意英雄都支持眩晕或射箭，但实际调用可能什么也不发生。若使用抛异常替代空实现，问题会变成运行时失败；根源仍是接口划分不合理。

### 3. 修改的影响面不必要地扩大

假设给 `ISkill` 新增 `doHeal()`：所有 `implements ISkill` 的英雄都必须修改和重新编译，即使它们完全不需要治疗能力。接口的变化被扩散到了不相关的实现类，这违背了 ISP 希望降低耦合的目标。

## 四、哪里体现接口隔离原则：`ISP` 包

### 1. 按独立能力拆分为小接口

工程在 `ISP` 包中将技能拆为四个职责单一的接口：

| 接口 | 暴露的方法 | 表示的能力 |
| --- | --- | --- |
| `ISkillArchery` | `doArchery()` | 射箭 |
| `ISkillInvisible` | `doInvisible()` | 隐身/隐袭 |
| `ISkillSilent` | `doSilent()` | 沉默 |
| `ISkillVertigo` | `doVertigo()` | 眩晕 |

每个接口只描述一项稳定的技能能力，客户端可以仅依赖所需接口。

### 2. 实现类按需组合能力

`ISP/impl/HeroHouYi.java` 实现：

```java
implements ISkillArchery, ISkillInvisible, ISkillSilent
```

它没有实现 `ISkillVertigo`，因此不再需要无意义的 `doVertigo()` 空实现。

`ISP/impl/HeroLianPo.java` 实现：

```java
implements ISkillInvisible, ISkillSilent, ISkillVertigo
```

它不实现 `ISkillArchery`，也不再需要空的 `doArchery()`。每个英雄的类型合同与其真实能力一致。

### 3. 变化被隔离在相关范围内

以后若只调整眩晕技能的参数或规则，主要受影响的是 `ISkillVertigo` 与实现该接口的英雄；只会射箭的英雄无需修改。新增“治疗”能力时，只需增加 `ISkillHeal` 并让具备治疗能力的英雄实现它，不会污染既有技能接口。

## 五、测试代码与工程设计的进一步观察

`ISP/ApiTest.java` 调用了正例中的英雄对象，能够证明它们可执行各自拥有的技能；但测试变量仍声明为具体类：

```java
HeroHouYi heroHouYi = new HeroHouYi();
heroHouYi.doArchery();
```

这不违反 ISP，但还没有完全展示“客户端只依赖最小接口”的好处。若某个业务只关心射箭，更有表达力的写法是：

```java
ISkillArchery archer = new HeroHouYi();
archer.doArchery();
```

此时调用方只依赖 `ISkillArchery`；任何实现该接口的英雄都可以替换。类似地，眩晕相关业务可依赖 `ISkillVertigo`。

同时要注意：本案例按“技能”拆接口很适合演示。但实际项目应先识别客户端角色和业务变化方向，再决定接口边界。若所有客户端始终同时使用四项能力，拆成四个接口未必带来收益。

## 六、面试提问、追问与参考回答

### 1. 什么是接口隔离原则？

**回答：** 客户端不应该被强迫依赖它不使用的方法。设计接口时应提供面向特定角色的、小而内聚的接口，使实现类和调用方只依赖真正需要的能力，从而减少耦合和变更影响。

**追问：它与单一职责原则有什么区别？**

**回答：** 单一职责原则关注一个类或模块“为什么变化”，强调职责单一；接口隔离原则关注客户端“被迫依赖了什么”，强调接口不能臃肿。两者都会推动高内聚，但 ISP 的直接对象是接口及其使用者。

### 2. 如何从代码中识别违反 ISP 的味道？

**回答：** 常见信号包括：实现类频繁出现空方法、`UnsupportedOperationException`、方法仅为满足编译而存在；一个接口的实现类只使用其中少数方法；接口新增一个方法会导致大量无关实现类改动。本工程 `Common` 包中后羿的空 `doVertigo()` 和廉颇的空 `doArchery()` 就是典型信号。

**追问：空实现一定违反 ISP 吗？**

**回答：** 不一定。框架回调、模板方法或可选钩子中，空实现可能是合理的默认行为。关键是该方法是否属于实现类应承担的语义合同；若对象从业务上不支持该能力，却被迫实现它，通常说明接口拆分不当。

### 3. 接口拆得越细越好吗？

**回答：** 不好。过度拆分会出现大量只有一个方法、且总是一起变化和一起使用的接口，增加文件数量、组合复杂度和理解成本。应该按照客户端需求、业务内聚性和变化边界拆分；经常一起被使用、一起变化的操作可以保留在同一接口。

**追问：本例为什么可以按单个技能拆分？**

**回答：** 因为不同英雄的技能组合不同，且“射箭”和“眩晕”等能力可独立存在、独立扩展。拆分后能直接消除空实现，并允许业务只依赖某一种能力，收益明确。

### 4. ISP 与依赖倒置原则（DIP）如何配合？

**回答：** DIP 要求高层模块依赖抽象而非具体实现；ISP 让这个抽象保持小而贴合调用方。比如“远程攻击系统”依赖 `ISkillArchery`（DIP），而不是依赖具体的 `HeroHouYi`；它也无需依赖眩晕、沉默等无关接口（ISP）。

**追问：只使用接口就一定符合 ISP 吗？**

**回答：** 不一定。若这个接口本身像 `Common.ISkill` 一样包含许多无关方法，调用方虽然依赖了抽象，仍可能被迫依赖不需要的能力。是否符合 ISP 取决于接口粒度是否匹配客户端需求。

### 5. 如果项目已有一个大接口，如何渐进式改造？

**回答：** 先通过调用关系和变更历史找出稳定的客户端能力集合，定义新的小接口；让现有实现类逐步实现对应小接口；新业务优先依赖小接口；最后在兼容期结束后废弃大接口。若需兼容旧调用方，可用适配器过渡，避免一次性破坏所有调用点。

**追问：改造的风险是什么？**

**回答：** 主要风险是错误地按实现类而非客户端需求拆分，造成接口碎片化；以及接口语义变化导致旧调用方行为不一致。改造前应补足契约测试，明确每个小接口的行为、异常和边界条件。
