# 单一职责原则案例教学：视频用户权益服务

## 一、什么是单一职责原则？

单一职责原则（Single Responsibility Principle，SRP）是 SOLID 原则之一：**一个类、模块或函数应该只有一个引起它变化的原因。**

它常被简化成“一个类只做一件事”，但更准确的判断标准是“职责是否属于同一个变化原因”。如果一个类同时因用户类型规则、广告策略、存储方式、日志格式、支付规则等不同原因而修改，它就承担了过多职责；这些变化应被拆分到边界更清晰的模块中。

面试中可以这样回答：

> 单一职责原则要求将变化原因不同的职责隔离。它的目标是降低耦合、缩小修改影响面，使代码更容易测试和维护。职责不是按方法数量机械划分，而是按业务角色和变化原因划分；过度拆分同样会让系统变复杂。

一个简单示例：`OrderService` 若同时负责订单计算、数据库保存、发送短信和生成 PDF 发票，就会因四类不同需求变化而修改。可以将其分别交由定价、仓储、通知、发票等协作者处理，而 `OrderService` 只负责订单流程编排。

## 二、工程业务与结构

工程模拟视频平台针对不同用户提供不同权益：

| 用户类型 | 清晰度 | 广告策略 |
| --- | --- | --- |
| VIP 用户 | 1080P 蓝光 | 无广告 |
| 普通用户 | 720P 超清 | 有广告 |
| 访客用户 | 480P 高清 | 有广告 |

代码分成两组，用于对比：

| 区域 | 作用 | 核心类 |
| --- | --- | --- |
| `com.ivanzhao.design.common` | 未拆分职责的基础实现 / 反例 | `VideoUserService` |
| `com.ivanzhao.design.SRP` | 按用户权益策略拆分的实现 / 正例 | `IVideoUserService`、三个 `*VideoUserService` |
| `src/test/.../common` | 演示反例调用 | `common.ApiTest` |
| `src/test/.../SRP` | 演示 SRP 方案调用 | `SRP.ApiTest` |

调用关系可概括为：

```text
反例：调用方 ──用户类型字符串──► VideoUserService ──if / else──► 各类用户规则

正例：调用方 ──抽象接口──► IVideoUserService ◄── 各类用户权益实现
                                           ├── VipVideoUserService
                                           ├── OrdinaryVideoUserService
                                           └── GuestVideoUserService
```

## 三、哪里没有体现单一职责原则：`common` 包

`common/VideoUserService.java` 的 `serveGrade(String userType)` 使用 `if / else if` 同时处理 VIP、普通用户和访客用户：

```java
if ("VIP用户".equals(userType)) {
    // VIP 清晰度规则
} else if ("普通用户".equals(userType)) {
    // 普通用户清晰度规则
} else if ("访客用户".equals(userType)) {
    // 访客清晰度规则
}
```

该类至少会因不同用户类型的权益变化而修改：

- VIP 清晰度升级、广告规则变化时要修改它；
- 普通用户权益变化时也要修改它；
- 新增“学生会员”“临时试用用户”时仍要修改它。

因此，它把多个用户角色的权益规则集中在一个类中。随着用户类型增加，条件分支会继续膨胀，任何一类规则的改动都有可能影响同一个类，测试也要覆盖所有分支。就本案例要表达的“按不同用户服务职责拆分”而言，这是未遵循 SRP 的反例。

此外，`userType` 使用字符串传递，名称拼写或文案变化可能导致逻辑失效；这属于类型安全和扩展性问题，虽不等同于 SRP，但会放大集中式分支设计的维护成本。

## 四、哪里体现单一职责原则：`SRP` 包

### 1. 每个实现类负责一种用户的权益规则

`IVideoUserService` 定义了视频权益需要提供的两个行为：

```java
void definition();      // 输出视频清晰度权益
void advertisement();   // 输出广告权益
```

三个实现类将用户策略分开：

| 类 | 负责的单一业务角色 | 实现的权益 |
| --- | --- | --- |
| `VipVideoUserService` | VIP 用户视频权益 | 1080P、无广告 |
| `OrdinaryVideoUserService` | 普通用户视频权益 | 720P、有广告 |
| `GuestVideoUserService` | 访客用户视频权益 | 480P、有广告 |

例如，VIP 会员权益变更时，通常只需要修改 `VipVideoUserService`；访客权益变更则修改 `GuestVideoUserService`。不同用户规则的变化被隔离在不同类中，降低了修改影响面，这正是本工程体现 SRP 的主要位置。

### 2. 调用方依赖抽象，便于替换具体用户策略

`SRP/ApiTest.java` 通过接口类型接收访客服务：

```java
IVideoUserService guest = new GuestVideoUserService();
guest.advertisement();
guest.definition();
```

测试可以在不改调用方式的情况下替换为 VIP 或普通用户实现。这里也体现了依赖抽象的思想；它与 SRP 相互配合，但严格来说属于依赖倒置原则的关注点。

## 五、这套 SRP 方案的边界与可改进之处

### 1. `definition()` 与 `advertisement()` 是否意味着仍然违反 SRP？

不一定。本案例中，一个 `*VideoUserService` 的职责可以定义为“**维护某类用户的视频观看权益**”。清晰度和广告都是该权益的一部分，往往因同一个业务原因——该用户等级的权益政策变化——而一起被审视，因此放在同一个用户权益策略类中是合理的。

但如果清晰度由视频编码团队独立变更、广告由商业化团队独立变更，二者有独立的数据来源、发布节奏或规则引擎，那么 `IVideoUserService` 和各实现类就会有两个变化原因。此时可进一步抽取 `VideoDefinitionPolicy` 与 `AdvertisementPolicy`，再由用户权益配置进行组合。是否拆分应由实际变化边界决定。

### 2. 同一权益文案存在重复

普通用户和访客用户均输出“视频有广告”。少量演示代码可以接受；生产代码中，如果广告策略、清晰度策略是可组合的数据规则，建议将其配置化或提取为独立策略对象，避免相同规则复制到多个用户类。注意：消除重复是可维护性考虑，不应为了去重而破坏清晰的职责边界。

### 3. 类职责与输出职责仍混在一起

当前方法直接 `System.out.println`，既表达权益规则又决定控制台输出形式。若未来需要返回 API JSON、渲染页面或记录日志，展示方式会成为额外变化原因。更可扩展的写法是让服务返回结构化的权益对象（如 `VideoPrivilege`），再由接口层负责展示。

### 4. 新增用户类型仍需创建实现类

这在“每种用户等级是一个稳定且独立的策略”的场景下是正常的，且符合 SRP：新增学生会员只新增 `StudentVideoUserService`，不修改既有实现。若用户等级完全由运营配置且变化频繁，可将规则转向数据配置或规则引擎，而非持续增加 Java 类。

## 六、面试提问、追问与参考回答

### 1. 什么是单一职责原则？

**回答：** 一个类或模块应该只有一个导致它变化的原因。实践中要按业务职责和变化边界拆分代码，使一个模块只承担一类内聚工作，减少修改时的连锁影响。

**追问：是不是一个类只能有一个方法？**

**回答：** 不是。一个职责通常需要多个协作方法。关键不是方法数量，而是它们是否服务于同一业务职责、是否因同一类原因变化。例如本例某类用户的清晰度与广告权益都属于其观看权益策略，可以共存于同一类。

### 2. 本工程中 `VideoUserService` 的问题是什么？

**回答：** 它通过条件分支同时维护 VIP、普通和访客用户的权益，任一用户类型规则变化或新增类型都会修改同一个类。不同用户策略耦合在一起，违反了案例中按用户角色划分职责的目标。

**追问：只把 `if / else` 换成 `switch` 能解决吗？**

**回答：** 不能。`switch` 只改变语法，不改变集中处理多个用户策略这一职责混杂的问题。应将各类用户权益放入各自策略实现，或在规则高度动态时采用配置化模型。

### 3. 本例的 `SRP` 包如何体现单一职责？

**回答：** `VipVideoUserService`、`OrdinaryVideoUserService`、`GuestVideoUserService` 分别只负责一种用户的观看权益。VIP 规则变化主要影响 VIP 类，访客规则变化主要影响访客类，变化影响面被限制在对应实现中。

**追问：新增“学生会员”时需要修改旧类吗？**

**回答：** 通常不需要。新增 `StudentVideoUserService` 实现 `IVideoUserService`，再在对象创建或装配处选择它即可。这说明已有用户策略与新增策略相对隔离；对象创建处是否需要调整，是另一层的组合/工厂职责问题。

### 4. SRP 与开闭原则（OCP）有什么关系？

**回答：** SRP 先把不同变化原因分离，使每个模块的职责边界清楚；这样新增或修改某项规则时更容易通过增加新实现来扩展，而不是修改复杂的旧分支，从而有助于满足 OCP。两者关注点不同：SRP 关注“谁应该变化”，OCP 关注“如何面对扩展保持稳定”。

**追问：拆成很多小类一定更符合 OCP 吗？**

**回答：** 不一定。若拆分没有真实变化边界，只会带来过多间接层。应该先观察哪些规则独立变化、哪些操作总是一起变化，再选择合适粒度。

### 5. 如何判断一个类是否职责过多？

**回答：** 可以问三个问题：它会因为哪些不同角色或需求而变？这些变化能否独立测试和发布？类中是否存在不相干的字段、分支、依赖或提交历史？若答案表明存在多条独立变化轴，就应考虑拆分。

**追问：拆分后的类如何协作，避免散落？**

**回答：** 通过清晰的抽象接口、构造器注入和一个专门的编排者协作。编排者只协调流程，不承载各策略细节；具体规则仍留在职责单一的策略类中。

### 6. SRP 是否只适用于类？

**回答：** 不只适用于类。方法、模块、服务、数据库表甚至团队边界都可用“一个变化原因”来审视。粒度越大，越要关注职责边界和独立演进能力。

**追问：如果拆分会影响性能怎么办？**

**回答：** 先通过基准测试确认瓶颈。多数业务系统中，清晰边界带来的可维护性收益远大于少量方法调用开销；若确有性能热点，可在保持抽象边界的前提下缓存、批处理或在基础设施层优化，而不是过早把不相关职责重新混在一起。
