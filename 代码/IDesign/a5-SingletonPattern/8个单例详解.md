# 1.什么是单例模式

**单例模式（Singleton Pattern）** 属于创建型设计模式，其核心目的是**确保一个类在整个系统中只有一个实例，并提供一个全局访问点**。

实现单例模式通常需要满足三个基本要素：

1. **构造函数私有化**：防止外部直接通过 `new` 实例化对象。
2. **持有私有静态实例**：在类内部保存唯一的实例引用。
3. **提供公共静态访问方法**：通常为 `getInstance()`，供全局获取该唯一实例。

**单例模式的主要分类与实现方式**

按对象的创建时机，单例模式主要分为两大流派：**饿汉式**（类加载时即创建）和**懒汉式**（首次使用时才创建），在此基础上演进出多种保证线程安全与性能的具体实现：

饿汉式：类初始化时直接创建对象，而不是等调用获取方法时再创建。

# 2.8种常见的单例模式

普通模式：

```java
//初始案例，非单例模式
public class Singleton_00 {

    public static Map<String,String> cache = new ConcurrentHashMap<>();

}
```

### （1）懒汉式单例模式

```java
//懒汉式单例模式：存在线程安全问题
public class Singleton_01 {

    // 静态成员变量：整个类只维护这一份 instance 引用
    // 初始值为 null，此时还没有创建 Singleton_01 对象
    private static Singleton_01 instance;

    // 私有构造方法：禁止外部通过 new 创建对象
    // 对象的创建权被限制在 Singleton_01 类内部
    private Singleton_01() {
    }

    // 静态方法：外部可以直接通过 Singleton_01.getInstance() 获取对象
    public static Singleton_01 getInstance() {

        // 第一次调用时，instance == null
        // 创建 Singleton_01 对象，并让 instance 指向这个对象
        if (instance == null) {
            instance = new Singleton_01();
        }

        // 第一次调用：返回刚创建的对象
        // 后续调用：instance 已经指向原来的对象，直接返回同一个对象
        return instance;
    }
}
```

### （2）同步懒汉式单例模式

```java
//同步懒汉式单例模式：没有线程安全问题
public class Singleton_02 {
    // 保存唯一的实例
    private static Singleton_02 instance;
    // 私有构造方法，禁止外部直接 new
    private Singleton_02() {
    }
    // 获取唯一实例
    // static synchronized属于锁住了Singleton_02这个类，不可以并发了
    // synchronized属于锁住了Singleton_02创建的对象，因此还可以并发
    public static synchronized Singleton_02 getInstance() {
        if (instance == null) {
            instance = new Singleton_02();
        }
        return instance;
    }
}
```

释义：

> ### 2. 先不要急着看 synchronized，先理解它为什么是单例
>
> 这段代码：
>
> ```
> private static Singleton_02 instance;
> ```
>
> 非常重要。
>
> 它定义了一个：
>
> > **静态的 Singleton_02 类型引用**
>
> 一开始：
>
> ```
> instance
>    ↓
>  null
> ```
>
> 注意，此时**还没有创建 Singleton_02 对象**。
>
> ------
>
> 然后：
>
> ```
> private Singleton_02() {
> }
> ```
>
> 构造方法是 `private`。
>
> 因此外部代码不能：
>
> ```
> Singleton_02 s = new Singleton_02();
> ```
>
> 编译器直接报错。
>
> 也就是说：
>
> > **对象创建权被 Singleton_02 自己收回来了。**
>
> 外部不能自己 `new`。
>
> ------
>
> 然后外部只能：
>
> ```
> Singleton_02.getInstance();
> ```
>
> 进入：
>
> ```
> public static synchronized Singleton_02 getInstance()
> ```
>
> 由这个方法负责决定：
>
> > 到底创建对象，还是把以前的对象返回出去。
>
> ------
>
> ### 3. 第一次调用到底发生什么？
>
> 假设：
>
> ```
> Singleton_02 s1 = Singleton_02.getInstance();
> ```
>
> 第一次执行：
>
> ```
> if (instance == null) {
>     instance = new Singleton_02();
> }
> ```
>
> 此时：
>
> ```
> instance == null
> ```
>
> 所以进入：
>
> ```
> instance = new Singleton_02();
> ```
>
> 这里发生了两件事情。
>
> ### 第一步：`new Singleton_02()`
>
> 创建对象：
>
> ```
>       Singleton_02对象①
>              ↑
>              │
> instance ────┘
> ```
>
> ### 第二步：
>
> ```
> instance = ...
> ```
>
> 让静态变量 `instance` 指向这个对象。
>
> 最终：
>
> ```
> Singleton_02
>      │
>      └── static instance
>              │
>              ↓
>         Singleton对象①
> ```
>
> 然后：
>
> ```
> return instance;
> ```
>
> 返回：
>
> ```
> 对象①
> ```
>
> 所以：
>
> ```
> s1
>  ↓
> 对象①
> ```
>
> ------
>
> ### 4. 第二次调用发生什么？
>
> 再执行：
>
> ```
> Singleton_02 s2 = Singleton_02.getInstance();
> ```
>
> 进入：
>
> ```
> if (instance == null)
> ```
>
> 但是现在：
>
> ```
> instance
>    ↓
> 对象①
> ```
>
> 所以：
>
> ```
> instance == null
> ```
>
> 结果是：
>
> ```
> false
> ```
>
> 不会执行：
>
> ```
> new Singleton_02()
> ```
>
> 而是：
>
> ```
> return instance;
> ```
>
> 于是：
>
> ```
> instance ──→ 对象①
>               ↑
>              / \
>            s1   s2
> ```
>
> 所以：
>
> ```
> s1 == s2
> ```
>
> 结果：
>
> ```
> true
> ```
>
> 这就是单例。
>
> ------
>
> ### 6. 那么 `synchronized` 到底有什么作用？
>
> 现在我们才来看：
>
> ```
> public static synchronized Singleton_02 getInstance()
> ```
>
> 这里的：
>
> ```
> synchronized
> ```
>
> 不是用来“让它成为单例”的唯一条件。
>
> 而是用来解决：
>
> > **多线程环境下，多个线程同时创建对象的问题。**
>
> 这是一个非常重要的区分。
>
> 单例本身主要靠：
>
> ```
> private 构造器
> +
> static instance
> +
> 统一获取入口
> ```
>
> 而 `synchronized` 是进一步解决：
>
> > **并发安全问题。**
>
> ------
>
> ### 7. 如果没有 synchronized，会发生什么？
>
> 假设我们改成：
>
> ```
> public static Singleton_02 getInstance() {
> 
>     if (instance == null) {
>         instance = new Singleton_02();
>     }
> 
>     return instance;
> }
> ```
>
> 单线程：
>
> ```
> 第一次 → 创建对象①
> 第二次 → 返回对象①
> 第三次 → 返回对象①
> ```
>
> 看起来完全没问题。
>
> 但是多线程下：
>
> ```
> 线程A                         线程B
> 
> getInstance()                 getInstance()
>      ↓                             ↓
> instance == null              instance == null
>      ↓                             ↓
>      true                          true
>      ↓                             ↓
> new Singleton_02()             new Singleton_02()
>      ↓                             ↓
>    对象①                          对象②
> ```
>
> 最终可能：
>
> ```
> 线程A → 对象①
> 
> 线程B → 对象②
> ```
>
> 这就破坏了单例。
>
> ------
>
> ### 8. `synchronized` 怎么解决？
>
> 现在：
>
> ```
> public static synchronized Singleton_02 getInstance()
> ```
>
> 意味着：
>
> > **同一时刻只能有一个线程执行这个方法。**
>
> 可以想象成：
>
> ```
>               getInstance()
>                     🔒
>                      │
>              同一时间一个线程
>                      │
>         ┌────────────┴────────────┐
>         ↓                         ↓
>      线程A进入                  线程B等待
> ```
>
> 例如线程 A 先进去：
>
> ```
> 线程A
>  ↓
> instance == null
>  ↓
> new Singleton_02()
>  ↓
> instance → 对象①
>  ↓
> return 对象①
>  ↓
> 释放锁
> ```
>
> 然后线程 B 才能进入：
>
> ```
> 线程B
>  ↓
> instance == null
>  ↓
> false
>  ↓
> return instance
>  ↓
> 对象①
> ```
>
> 所以：
>
> ```
> 线程A ──→ 对象①
> 线程B ──→ 对象①
> ```
>
> 这就安全了。
>
> ------
>
> ### 9. 为什么这里是 `static synchronized`？
>
> 这个地方非常值得你搞懂。
>
> 你写的是：
>
> ```
> public static synchronized Singleton_02 getInstance()
> ```
>
> 这里同时有：
>
> ```
> static
> ```
>
> 和：
>
> ```
> synchronized
> ```
>
> 为什么？
>
> 因为外部调用：
>
> ```
> Singleton_02.getInstance();
> ```
>
> 的时候，还没有 Singleton 对象。
>
> 所以 `getInstance()` 必须是：
>
> ```
> static
> ```
>
> 这样才能直接通过类调用：
>
> ```
> Singleton_02.getInstance();
> ```
>
> ------
>
> 而：
>
> ```
> synchronized
> ```
>
> 需要锁住某个东西。
>
> 对于**静态同步方法**：
>
> ```
> public static synchronized void test()
> ```
>
> 锁的是：
>
> ```
> Singleton_02.class
> ```
>
> 也就是这个类对应的 `Class` 对象。
>
> 所以：
>
> ```
> public static synchronized Singleton_02 getInstance()
> ```
>
> 可以理解为：
>
> ```
> public static Singleton_02 getInstance() {
> 
>     synchronized (Singleton_02.class) {
> 
>         if (instance == null) {
>             instance = new Singleton_02();
>         }
> 
>         return instance;
>     }
> }
> ```
>
> 两者在同步语义上是等价的。
>
> ------
>
> ### 10. 这里要特别区分 `synchronized` 锁什么
>
> 这是 Java 面试非常常见的问题。
>
> ### 普通实例同步方法
>
> ```
> public synchronized void test() {
> }
> ```
>
> 锁：
>
> ```
> this
> ```
>
> 也就是当前对象。
>
> ------
>
> ### 静态同步方法
>
> ```
> public static synchronized void test() {
> }
> ```
>
> 锁：
>
> ```
> Singleton_02.class
> ```
>
> 也就是类对象。
>
> ------
>
> ### 同步代码块
>
> ```
> synchronized (obj) {
> }
> ```
>
> 锁：
>
> ```
> obj
> ```
>
> 所以你可以记：
>
> | 写法                           | 锁           |
> | ------------------------------ | ------------ |
> | `synchronized` 实例方法        | `this`       |
> | `static synchronized` 静态方法 | `类名.class` |
> | `synchronized(obj)`            | `obj`        |
>
> ------
>
> ### 11. 为什么这个叫“懒汉式”？
>
> 看：
>
> ```
> private static Singleton_02 instance;
> ```
>
> 初始化时：
>
> ```
> instance → null
> ```
>
> 没有创建对象。
>
> 只有第一次：
>
> ```
> Singleton_02.getInstance();
> ```
>
> 才：
>
> ```
> instance = new Singleton_02();
> ```
>
> 所以：
>
> > **需要的时候才创建。**
>
> 因此叫：
>
> > **懒加载 / 懒汉式**
>
> 和饿汉式对比：
>
> ### 懒汉式
>
> ```
> private static Singleton instance;
> ```
>
> 第一次使用：
>
> ```
> getInstance()
>     ↓
> new
> ```
>
> ### 饿汉式
>
> ```
> private static final Singleton instance =
>         new Singleton();
> ```
>
> 类初始化时：
>
> ```
> 加载/初始化类
>       ↓
>     new
> ```
>
> ------
>

>
> ### 14. 这个版本到底解决了什么？
>
> 现在我们把每个关键代码对应起来：
>
> ```
> public class Singleton_02 {
> 
>     private static Singleton_02 instance;
> ```
>
> ### `static`
>
> 保证所有调用者共享同一个：
>
> ```
> instance
> ```
>
> ------
>
> ```
> private Singleton_02() {
> }
> ```
>
> ### `private`
>
> 禁止外部：
>
> ```
> new Singleton_02()
> ```
>
> ------
>
> ```
> public static synchronized Singleton_02 getInstance()
> ```
>
> ### `static`
>
> 允许：
>
> ```
> Singleton_02.getInstance()
> ```
>
> 在没有实例的情况下调用。
>
> ### `synchronized`
>
> 保证多个线程不能同时执行创建逻辑。
>
> ------
>
> ```
> if (instance == null) {
> ```
>
> 检查：
>
> > 有没有创建过实例？
>
> ------
>
> ```
> instance = new Singleton_02();
> ```
>
> 如果没有：
>
> > 创建唯一实例，并保存起来。
>
> ------
>
> ```
> return instance;
> ```
>
> 以后：
>
> > 永远返回这个保存的实例。
>
> ------
>
> ### 15. 最后把整个过程压缩成一张图
>
> 第一次调用：
>
> ```
> Singleton_02.getInstance()
>              │
>              ↓
>       获取 Singleton.class 锁
>              │
>              ↓
>       instance == null ?
>              │
>             YES
>              ↓
>       new Singleton_02()
>              │
>              ↓
>           对象①
>              │
>              ↓
>    instance ─────────→ 对象①
>              │
>              ↓
>         return 对象①
>              │
>              ↓
>           释放锁
> ```
>
> 第二次调用：
>
> ```
> Singleton_02.getInstance()
>              │
>              ↓
>       获取 Singleton.class 锁
>              │
>              ↓
>       instance == null ?
>              │
>              NO
>              ↓
>    return instance
>              │
>              ↓
>           对象①
> ```
>
> 所以最终：
>
> ```
>                 Singleton_02
>                      │
>              static instance
>                      │
>                      ↓
>                   对象①
>                  ↗     ↖
>                s1       s2
> ```
>

>
> ### 16. 这一版单例的优缺点
>
> ### 优点
>
> **① 懒加载**
>
> 对象真正需要时才创建。
>
> **② 线程安全**
>
> `synchronized` 保证同一时刻只有一个线程执行 `getInstance()`。
>
> **③ 实现简单**
>
> 代码非常容易理解：
>
> ```
> if (instance == null) {
>     instance = new Singleton_02();
> }
> return instance;
> ```
>
> ------
>
> ### 缺点
>
> 最大的问题是：
>
> > **每次调用 `getInstance()` 都要进入 synchronized 方法。**
>
> 即使对象早就已经创建：
>
> ```
> instance → 对象①
> ```
>
> 之后：
>
> ```
> Singleton_02.getInstance();
> ```
>
> 仍然需要获取同步锁。
>
> 所以它是：
>
> ```
> 线程安全 ✅
> 懒加载   ✅
> 实现简单 ✅
> ```
>
> 但是：
>
> ```
> 每次获取都需要同步 ❌
> ```
>
> 这也是后来为什么出现：
>
> > **DCL（双重检查锁）**
>
> 的原因。
>
> ------
>
> ### 17. 你现在可以把 Singleton_01 → Singleton_05 看成一个演进过程
>
> 这其实比单独背每个代码重要得多：
>
> ```
> Singleton_01
> 简单懒汉
>     │
>     │ 发现多线程不安全
>     ↓
> Singleton_02
> synchronized 懒汉
>     │
>     │ 发现每次获取都需要加锁
>     ↓
> Singleton_04 / Singleton_05
> 静态内部类 / DCL
>     │
>     │
>     ├── 静态内部类：
>     │      利用 JVM 类初始化机制
>     │
>     └── DCL：
>            volatile + synchronized
> ```
>
> 所以你现在研究 `Singleton_02`，**真正应该吃透的不是“这是一个单例模式”这句话，而是这几个知识点之间的关系：**
>
> ```
> private
>   ↓
> 禁止外部 new
> 
> static
>   ↓
> 保存全局唯一引用
> 
> getInstance()
>   ↓
> 提供统一访问入口
> 
> lazy initialization
>   ↓
> 第一次使用才 new
> 
> synchronized
>   ↓
> 解决多线程同时创建的问题
> 
> static synchronized
>   ↓
> 锁 Singleton_02.class
> ```

### （3）饿汉式单例模式

```java
// 饿汉式单例:类一加载/初始化，就立即创建对象，不管你以后用不用。
// Singleton_03 是饿汉式单例模式。通过 private 构造方法禁止外部创建对象，
// 通过 static final 持有类级别的唯一实例，并通过 getInstance() 提供统一访问入口。
// 实例在类初始化阶段就被创建，因此不需要额外的同步机制，天然具有线程安全性。
public class Singleton_03 {

    // 静态成员变量：整个类只有这一份 instance 引用
    // 类初始化时就创建 Singleton_03 对象
    // 加上final的原因：instance 这个引用初始化之后，不能再重新指向其他对象。
    private static final Singleton_03 instance = new Singleton_03();

    // 私有构造方法：禁止外部通过 new 创建对象
    private Singleton_03() {
    }

    // 静态方法：通过类名直接获取唯一实例
    public static Singleton_03 getInstance() {
        return instance;
    }
}

```

释义：

> 这里我只增加了：
>
> ```
> final
> ```
>
> 原来的：
>
> ```
> private static Singleton_03 instance = new Singleton_03();
> ```
>
> 改成：
>
> ```
> private static final Singleton_03 instance = new Singleton_03();
> ```
>
> 为什么可以加 `final`？
>
> 因为这个 `instance` 从设计上就**不应该再指向其他对象**。
>
> 也就是说：
>
> ```
> instance = new Singleton_03();
> ```
>
> 只应该发生一次。
>
> 所以：
>
> ```
> final
> ```
>
> 正好表达了：
>
> > `instance` 这个引用初始化之后，不能再重新指向其他对象。
>
> ------
>
> ### 2. 它为什么是单例模式？
>
> 判断一个类是不是单例，核心看两个东西。
>
> ### 第一：外部不能随便 `new`
>
> ```
> private Singleton_03() {
> }
> ```
>
> 构造方法是 `private`。
>
> 所以外部：
>
> ```
> Singleton_03 s = new Singleton_03();
> ```
>
> 直接编译错误。
>
> 也就是说：
>
> > 外部代码没有权限创建 `Singleton_03` 对象。
>
> ------
>
> ### 第二：类内部只维护一个实例
>
> ```
> private static final Singleton_03 instance = new Singleton_03();
> ```
>
> 这里非常关键。
>
> 我们拆开来看：
>
> ```
> static
> ```
>
> 意味着 `instance` 属于 **Singleton_03 这个类**，而不是某一个具体的对象。
>
> 所以整个 JVM 中，这个类对应的这份静态字段只有一份。
>
> 而：
>
> ```
> new Singleton_03()
> ```
>
> 创建了一个真正的 `Singleton_03` 对象。
>
> 于是：
>
> ```
> Singleton_03 类
>        │
>        │ static
>        ↓
> instance 引用
>        │
>        ↓
>    ┌──────────┐
>    │ Object①  │
>    │ Singleton_03 │
>    └──────────┘
> ```
>
> 然后：
>
> ```
> public static Singleton_03 getInstance() {
>     return instance;
> }
> ```
>
> 所有人都从这个入口拿这个对象。
>
> 所以：
>
> ```
> 调用者 A ─────┐
>               ↓
>          getInstance()
>               ↓
>          instance
>               ↓
>            Object①
> 
> 调用者 B ─────┘
> ```
>
> A 和 B 最终拿到的是**同一个对象**。
>
> ------
>
> ### 3. 这个单例最重要的特点：饿汉式
>
> 这个实现叫：
>
> > **饿汉式单例（Eager Singleton）**
>
> 为什么叫“饿汉式”？
>
> 因为它是：
>
> > **类一加载/初始化，就立即创建对象，不管你以后用不用。**
>
> 看这里：
>
> ```
> private static final Singleton_03 instance = new Singleton_03();
> ```
>
> 注意：
>
> ```
> new Singleton_03()
> ```
>
> 不是发生在：
>
> ```
> getInstance()
> ```
>
> 里面。
>
> 而是在类初始化阶段就发生了。
>
> 所以整个过程是：
>
> ```
> Singleton_03 类初始化
>         ↓
> 执行静态字段初始化
>         ↓
> new Singleton_03()
>         ↓
> 创建 Object①
>         ↓
> instance → Object①
>         ↓
> 类初始化完成
> ```
>
> 之后你调用：
>
> ```
> getInstance()
> ```
>
> 根本不需要创建对象。
>
> 只是：
>
> ```
> getInstance()
>       ↓
> return instance
>       ↓
> Object①
> ```
>
> ------
>
> ### 4. 和前面的 Singleton_02 对比一下
>
> 这两个非常值得放在一起看。
>
> ### Singleton_02：懒汉式
>
> ```java
> public class Singleton_02 {
> 
>     private static Singleton_02 instance;
> 
>     private Singleton_02() {
>     }
> 
>     public static synchronized Singleton_02 getInstance() {
>         if (instance == null) {
>             instance = new Singleton_02();
>         }
> 
>         return instance;
>     }
> }
> ```
>
> 第一次调用：
>
> ```
> Singleton_02.getInstance();
> ```
>
> 才：
>
> ```
> instance == null
>       ↓
> new Singleton_02()
>       ↓
> 创建对象
> ```
>
> 所以叫：
>
> > **懒汉式：需要的时候才创建。**
>
> ------
>
> ### Singleton_03：饿汉式
>
> ```
> private static final Singleton_03 instance = new Singleton_03();
> ```
>
> 类初始化的时候：
>
> ```
> 类初始化
>    ↓
> 立即 new
>    ↓
> Object①
> ```
>
> 即使你从来没有调用：
>
> ```
> getInstance()
> ```
>
> 这个对象也已经创建了。
>
> 所以叫：
>
> > **饿汉式：不等你调用，先把对象创建好。**
>
> ------
>
> ### 5. 那它为什么不需要 `synchronized`？
>
> 这是这个实现最值得你理解的地方。
>
> 你可能会想：
>
> > `Singleton_02` 为了线程安全，需要 `synchronized`，为什么 `Singleton_03` 不需要？
>
> 因为：
>
> ### `Singleton_03` 根本不存在“多个线程同时创建对象”的问题。
>
> 对象创建发生在：
>
> ```
> private static final Singleton_03 instance = new Singleton_03();
> ```
>
> 也就是**类初始化阶段**。
>
> Java 的类初始化机制本身就保证：
>
> > 一个类的初始化过程在多线程环境下只会被安全地执行一次。
>
> 所以：
>
> ```
> 线程A ──┐
>         │
> 线程B ──┼──> Singleton_03 类初始化
>         │
> 线程C ──┘
>               ↓
>         JVM保证初始化安全
>               ↓
>         new Singleton_03()
>               ↓
>            Object①
> ```
>
> 不会出现：
>
> ```
> 线程A → new Object①
> 线程B → new Object②
> 线程C → new Object③
> ```
>
> 这种情况。
>
> 因此它天然是线程安全的。
>
> ------
>
> ### 6. 你可以把两个版本的创建时机画成这样
>
> ### Singleton_02：懒汉式
>
> ```
> 程序启动
>    │
>    ↓
> instance = null
>    │
>    │
>    │    此时还没有对象
>    │
>    ↓
> 某个线程调用 getInstance()
>    │
>    ↓
> instance == null
>    │
>    ↓
> new Singleton_02()
>    │
>    ↓
> Object①
>    │
>    ↓
> instance → Object①
> ```
>
> ------
>
> ### Singleton_03：饿汉式
>
> ```
> 类初始化
>    │
>    ↓
> private static final Singleton_03 instance
>    │
>    ↓
> new Singleton_03()
>    │
>    ↓
> Object①
>    │
>    ↓
> instance → Object①
>    │
>    ↓
> 类初始化完成
>    │
>    ↓
> 以后 getInstance()
>    │
>    ↓
> 直接 return instance
> ```
>
> 所以两者最大的区别其实就是：
>
> > **对象到底什么时候创建。**
>
> ------
>
> ### 7. 演示一下如何调用
>
> 我们写一个测试类：
>
> ```java
> public class SingletonTest {
> 
>     public static void main(String[] args) {
> 
>         // 第一次获取单例对象
>         Singleton_03 s1 = Singleton_03.getInstance();
> 
>         // 第二次获取单例对象
>         Singleton_03 s2 = Singleton_03.getInstance();
> 
>         // 比较两个引用是否指向同一个对象
>         System.out.println(s1 == s2);
>     }
> }
> ```
>
> 运行结果：
>
> ```
> true
> ```
>
> 为什么？
>
> 我们一步一步看。
>
> 第一次：
>
> ```
> Singleton_03 s1 = Singleton_03.getInstance();
> ```
>
> 实际上：
>
> ```
> Singleton_03.getInstance()
>           ↓
>       return instance
>           ↓
>        Object①
>           ↓
> s1 ───────┘
> ```
>
> 第二次：
>
> ```
> Singleton_03 s2 = Singleton_03.getInstance();
> ```
>
> 还是：
>
> ```
> Singleton_03.getInstance()
>           ↓
>       return instance
>           ↓
>        Object①
>           ↓
> s2 ───────┘
> ```
>
> 最终：
>
> ```
>              ┌───────────────┐
>              │   Object①     │
>              │ Singleton_03  │
>              └───────────────┘
>                 ↑         ↑
>                 │         │
>                s1        s2
> ```
>

>
> ```
> s1 == s2
> ```
>
> 结果就是：
>
> ```

> ```
>

>
> > **两个引用是否指向同一个对象。**
>
> 不是比较两个对象的内容。
>
> ------
>
> ### 8. 再验证一下：外部真的不能 `new`
>
> 你可以试试：
>
> ```
> public class SingletonTest {
> 
>     public static void main(String[] args) {
> 
>         Singleton_03 s1 = Singleton_03.getInstance();
> 
>         Singleton_03 s2 = new Singleton_03();
>     }
> }
> ```
>
> 第二行会报错：
>
> ```
> Singleton_03() has private access in Singleton_03
> ```
>
> 因为：
>
> ```
> private Singleton_03() {
> }
> ```
>
> 构造方法只能在 `Singleton_03` 类内部使用。
>
> 这就是单例模式非常核心的一个设计：
>
> ```
> 外部
>  │
>  ├── new Singleton_03()     ❌
>  │
>  └── getInstance()          ✅
>                               │
>                               ↓
>                            Object①
> ```
>
> 也就是说：
>
> > **把对象的创建权收回到类内部，把对象的获取权开放给外部。**
>
> ------
>
> ### 9. 为什么这里推荐 `final`？
>
> 这个地方你可以顺便理解一下 `final` 在单例里的作用。
>
> ```
> private static final Singleton_03 instance = new Singleton_03();
> ```
>
> 可以拆成：
>
> ```
> private
>    ↓
> 外部不能直接访问
> 
> static
>    ↓
> 属于类，整个类共享这一份引用
> 
> final
>    ↓
> 初始化之后，这个引用不能再改变
> 
> Singleton_03
>    ↓
> 引用类型
> 
> instance
>    ↓
> 引用变量
> 
> new Singleton_03()
>    ↓
> 真正创建对象
> ```
>
> 尤其注意：
>
> ```
> final
> ```
>
> 限制的是：
>
> > **引用不能重新指向另一个对象。**
>
> 不是说这个对象本身不能修改。
>
> 例如：
>
> ```
> final Singleton_03 instance = new Singleton_03();
> ```
>
> 不能：
>
> ```
> instance = new Singleton_03(); // ❌
> ```
>
> 但如果 `Singleton_03` 里面存在普通可变字段：
>
> ```
> instance.setName("Tom"); // ✅
> ```
>
> 仍然可以修改对象内部状态。
>
> ------
>
> ### 10. 这个单例的优缺点
>
> ### 优点
>
> **① 简单**
>
> 代码非常少：
>
> ```
> private static final Singleton_03 instance = new Singleton_03();
> 
> private Singleton_03() {}
> 
> public static Singleton_03 getInstance() {
>     return instance;
> }
> ```
>
> ------
>
> **② 天然线程安全**
>
> 不需要：
>
> ```
> synchronized
> ```
>
> 不需要：
>
> ```
> volatile
> ```
>
> 不需要：
>
> ```
> AtomicReference
> ```
>
> 因为依赖 Java 类初始化机制。
>
> ------
>
> **③ 获取对象非常简单**
>
> 后续：
>
> ```
> Singleton_03.getInstance()
> ```
>
> 本质就是直接：
>
> ```
> return instance;
> ```
>
> 没有锁竞争。
>
> ------
>
> ### 缺点
>
> 最大的问题：
>
> > **不支持真正的懒加载。**
>
> 假设这个对象非常重：
>
> ```
> private static final Singleton_03 instance = new Singleton_03();
> ```
>
> 一旦类初始化，就创建它。
>
> 即使整个程序：
>
> ```
> Singleton_03.getInstance();
> ```
>
> 一次都没调用。
>
> 对象依然已经创建了。
>
> 例如：
>
> ```
> public Singleton_03() {
> 
>     // 假设这里初始化很重
>     // 加载大量配置
>     // 创建大量资源
>     // 建立连接……
> }
> ```
>
> 那么饿汉式就可能产生不必要的初始化成本。
>
> 当然，现实中的具体成本取决于对象本身；不能简单说“饿汉式一定浪费”。
>
> ------
>
> ### 11. 最后把 Singleton_03 记成一个完整模型
>
> 你现在不要把它死记成一句：
>
> > “饿汉式单例。”
>
> 最好记成下面这个逻辑：
>
> ```
>                  Singleton_03
>                       │
>              private 构造方法
>                       │
>              外部不能 new
>                       │
>                       ↓
>         static final instance
>                       │
>           类初始化时立即 new
>                       │
>                       ↓
>                   Object①
>                       ↑
>                       │
>               getInstance()
>                       │
>                  return instance
>                       │
>           ┌───────────┴───────────┐
>           ↓                       ↓
>          s1                      s2
>           │                       │
>           └──────── Object① ──────┘
> ```
>
> 因此它的完整特征是：
>
> > **`Singleton_03` 是饿汉式单例模式。通过 `private` 构造方法禁止外部创建对象，通过 `static final` 持有类级别的唯一实例，并通过 `getInstance()` 提供统一访问入口。实例在类初始化阶段就被创建，因此不需要额外的同步机制，天然具有线程安全性。**

### （4）懒汉式静态内部类单例

```java
//懒汉式：静态内部类单例 / Holder 模式
// 利用静态内部类只有在第一次主动使用时才初始化的特性，
// 把单例对象的创建延迟到 getInstance() 第一次调用，同时利用 JVM 的类初始化机制保证线程安全。
public class Singleton_04 {
    // 静态内部类
    // 注意：这里并不会在 Singleton_04 加载时立即创建 Singleton_04 对象
    // 把 Singleton_04 实例的创建时机推迟到 SingletonHolder(静态内部类) 被初始化的时候。
    private static class SingletonHolder {
        // SingletonHolder 初始化时，才创建 Singleton_04 对象
        private static final Singleton_04 instance = new Singleton_04();
    }

    // 私有构造方法：禁止外部通过 new 创建 Singleton_04 对象
    private Singleton_04() {
    }

    // 对外提供唯一的实例获取入口
    public static Singleton_04 getInstance() {
        // 第一次访问 SingletonHolder.instance 时，
        // JVM 会初始化 SingletonHolder 类
        // 初始化过程中执行：
        // new Singleton_04()
        return SingletonHolder.instance;
    }
}
```

释义：

> ### 3. 最容易搞混的地方：到底什么时候 `new`？
>
> 你看：
>
> ```
> private static class SingletonHolder {
>     private static final Singleton_04 instance = new Singleton_04();
> }
> ```
>
> 可能第一眼会觉得：
>
> > “既然这里写了 `new Singleton_04()`，那不是类加载的时候就创建了吗？”
>
> **不是。**
>
> 这是理解 Holder 模式最关键的一点。
>
> Java 有一个重要机制：
>
> > **类的加载、链接、初始化不是一回事。**
>
> 对于这里，我们重点理解“初始化”。
>
> ------
>
> ### 4. `Singleton_04` 和 `SingletonHolder` 是两个不同的类
>
> 这一点一定要先建立起来。
>
> 代码：
>
> ```
> public class Singleton_04 {
> 
>     private static class SingletonHolder {
> 
>         private static final Singleton_04 instance =
>                 new Singleton_04();
>     }
> }
> ```
>
> 实际上定义了两个类：
>
> ```
> Singleton_04
> │
> └── SingletonHolder
> ```
>
> 其中：
>
> ```
> Singleton_04
> ```
>
> 是外部类。
>
> 而：
>
> ```
> SingletonHolder
> ```
>
> 是一个**静态内部类**。
>
> 注意：
>
> > `static class SingletonHolder` 本身也是一个类。
>
> 它不是 `Singleton_04` 的一个对象。
>
> ------
>
> ### 5. 为什么要搞一个 SingletonHolder？
>
> 目的就是：
>
> > **把 Singleton_04 实例的创建时机推迟到 SingletonHolder 被初始化的时候。**
>
> 看这两个版本。
>
> ### Singleton_03
>
> ```java
> public class Singleton_03 {
> 
>     private static final Singleton_03 instance =
>             new Singleton_03();
> 
>     private Singleton_03() {}
> 
>     public static Singleton_03 getInstance() {
>         return instance;
>     }
> }
> ```
>
> 这里：
>
> ```
> new Singleton_03()
> ```
>
> 属于：
>
> ```
> Singleton_03
> ```
>
> 自己的静态字段初始化。
>
> 所以：
>
> ```
> Singleton_03 初始化
>        ↓
> new Singleton_03()
>        ↓
> 创建实例
> ```
>
> ------
>
> ### Singleton_04
>
> 变成：
>
> ```
> private static class SingletonHolder {
> 
>     private static final Singleton_04 instance =
>             new Singleton_04();
> }
> ```
>
> 于是：
>
> ```
> Singleton_04 初始化
>        ↓
> 不会立即初始化 SingletonHolder
>        ↓
> 也就不会执行 new Singleton_04()
> ```
>
> 真正第一次执行：
>
> ```
> Singleton_04.getInstance();
> ```
>
> 时：
>
> ```
> return SingletonHolder.instance;
> ```
>
> 程序第一次主动使用：
>
> ```
> SingletonHolder.instance
> ```
>
> 于是 JVM 才初始化：
>
> ```
> SingletonHolder
>        ↓
> 执行静态字段初始化
>        ↓
> new Singleton_04()
>        ↓
> 创建 Object①
> ```
>
> 这就是所谓的：
>
> > **按需初始化（lazy initialization）**
>
> ------
>
> ### 6. 第一次调用到底发生了什么？
>
> 假设：
>
> ```
> Singleton_04 s1 = Singleton_04.getInstance();
> ```
>
> 我们一步一步追踪。
>
> ------
>
> ### 第一步：调用静态方法
>
> ```
> Singleton_04.getInstance();
> ```
>
> 进入：
>
> ```
> public static Singleton_04 getInstance() {
>     return SingletonHolder.instance;
> }
> ```
>
> ------
>
> ### 第二步：访问 `SingletonHolder.instance`
>
> 程序执行：
>
> ```
> SingletonHolder.instance
> ```
>
> 此时 JVM 发现：
>
> > `SingletonHolder` 还没有完成初始化。
>
> 于是开始初始化 `SingletonHolder`。
>
> ------
>
> ### 第三步：执行静态字段初始化
>
> 执行：
>
> ```
> private static final Singleton_04 instance =
>         new Singleton_04();
> ```
>
> 于是：
>
> ```
> new Singleton_04()
>        ↓
> Object①
>        ↓
> SingletonHolder.instance
>        ↓
> Object①
> ```
>
> ------
>
> ### 第四步：返回对象
>
> 最终：
>
> ```
> return SingletonHolder.instance;
> ```
>
> 返回：
>
> ```
> Object①
> ```
>
> 于是：
>
> ```
> Singleton_04 s1 = Singleton_04.getInstance();
> ```
>
> 变成：
>
> ```
> s1 ──────────→ Object①
> ```
>
> ------
>
> ### 7. 第二次调用呢？
>
> 再来：
>
> ```
> Singleton_04 s2 = Singleton_04.getInstance();
> ```
>
> 还是：
>
> ```
> return SingletonHolder.instance;
> ```
>
> 但是这一次：
>
> ```
> SingletonHolder
>        ↓
> 已经初始化完成
>        ↓
> instance
>        ↓
> Object①
> ```
>
> 所以直接：
>
> ```
> s2 ──────────→ Object①
> ```
>
> 最终：
>
> ```
>              ┌──────────────┐
>              │   Object①    │
>              │ Singleton_04 │
>              └──────────────┘
>                 ↑         ↑
>                 │         │
>                s1        s2
> ```
>
> 因此：
>
> ```
> System.out.println(s1 == s2);
> ```
>
> 结果：
>
> ```
> true
> ```
>

>

> ```

> true

>                        ↑
>              ┌─────────┼─────────┐
>              │         │         │
>             s1        s2        s3
> ```

>
> ### 9. 最关键的问题：为什么线程安全？
>
> 这才是 Holder 模式真正厉害的地方。
>
> 你可能会问：
>
> > 第一次调用 `getInstance()` 的时候，如果有 100 个线程同时调用呢？
>
> 例如：
>
> ```
> 线程A ──→ getInstance()
> 线程B ──→ getInstance()
> 线程C ──→ getInstance()
> ...
> 线程100 ─→ getInstance()
> ```
>
> 它们都执行：
>
> ```
> SingletonHolder.instance
> ```
>
> 那么会不会：
>
> ```
> 线程A → new Singleton_04() → Object①
> 线程B → new Singleton_04() → Object②
> 线程C → new Singleton_04() → Object③
> ```
>
> **不会。**
>
> 因为 Java 的**类初始化机制本身具有线程安全保证**。
>
> 对于一个类：
>
> ```
> SingletonHolder
> ```
>
> 它的初始化过程由 JVM 保证：
>
> > **同一个类的初始化，在并发情况下只会成功执行一次。**
>
> 所以：
>
> ```
> 线程A ──┐
> 线程B ──┤
> 线程C ──┼──→ SingletonHolder 初始化
> 线程D ──┤
> ...     ┘
>               ↓
>          JVM 保证只初始化一次
>               ↓
>        new Singleton_04()
>               ↓
>             Object①
> ```
>
> 最终所有线程拿到：
>
> ```
> Object①
> ```
>
> ------
>
> ### 10. 所以它为什么不需要 `synchronized`？
>
> 因为你已经把：
>
> ```
> new Singleton_04()
> ```
>
> 放到了：
>
> ```
> SingletonHolder
> ```
>
> 的类初始化过程中。
>
> 而：
>
> > **类初始化本身就是 JVM 帮你做同步的。**
>
> 所以不需要自己写：
>
> ```
> synchronized
> ```
>
> 也不需要：
>
> ```
> volatile
> ```
>
> 更不需要：
>
> ```
> AtomicReference
> ```
>
> 这就是 Holder 模式非常漂亮的地方。
>
> ------
>
> ### 11. 和 Singleton_03 放在一起，你就彻底明白了
>
> 这是你刚才学的：
>
> ### Singleton_03
>
> ```java
> public class Singleton_03 {
> 
>     private static final Singleton_03 instance =
>             new Singleton_03();
> 
>     private Singleton_03() {}
> 
>     public static Singleton_03 getInstance() {
>         return instance;
>     }
> }
> ```
>
> 创建时机：
>
> ```
> Singleton_03 初始化
>        ↓
> new Singleton_03()
> ```
>
> 所以：
>
> > **饿汉式**
>
> ------
>
> ### Singleton_04
>
> ```java
> public class Singleton_04 {
> 
>     private static class SingletonHolder {
>         private static final Singleton_04 instance =
>                 new Singleton_04();
>     }
> 
>     private Singleton_04() {}
> 
>     public static Singleton_04 getInstance() {
>         return SingletonHolder.instance;
>     }
> }
> ```
>
> 创建时机：
>
> ```
> Singleton_04 初始化
>        ↓
> 不创建 Singleton_04
> 
> 第一次调用 getInstance()
>        ↓
> 访问 SingletonHolder.instance
>        ↓
> 初始化 SingletonHolder
>        ↓
> new Singleton_04()
> ```
>
> 所以：
>
> > **懒加载**
>
> ------
>
> ### 12. 两者真正的区别
>
> |                  | Singleton_03 | Singleton_04        |
> | ---------------- | ------------ | ------------------- |
> | 模式             | 饿汉式       | Holder / 静态内部类 |
> | 是否懒加载       | ❌            | ✅                   |
> | 线程安全         | ✅            | ✅                   |
> | `synchronized`   | 不需要       | 不需要              |
> | `volatile`       | 不需要       | 不需要              |
> | CAS              | 不需要       | 不需要              |
> | 实现复杂度       | 很低         | 低                  |
> | 第一次使用时创建 | ❌            | ✅                   |
> | 依赖机制         | 类初始化     | 静态内部类初始化    |
>
> 因此：
>
> ```
> Singleton_03
>     ↓
> 简单
>     ↓
> 但是提前创建
> 
> Singleton_04
>     ↓
> 同样简单
>     ↓
> 延迟创建
>     ↓
> 同时利用 JVM 类初始化机制保证线程安全
> ```
>
> 这就是为什么 **Holder 模式在 Java 中非常经典**。
>
> ------
>
> ### 13. 这里还有一个特别容易混淆的问题
>
> 你可能会看到：
>
> ```
> private static class SingletonHolder
> ```
>
> 然后产生一个疑问：
>
> > “SingletonHolder 是 static，那是不是 SingletonHolder 本身也是一个单例对象？”
>
> **不是。**
>
> 这里的 `static` 修饰的是**内部类的定义**。
>
> ```
> private static class SingletonHolder
> ```
>
> 表示：
>
> > `SingletonHolder` 是一个静态嵌套类，可以不依赖 `Singleton_04` 的实例存在。
>
> 它和：
>
> ```
> private static final Singleton_04 instance
> ```
>
> 里面的 `static` 不是同一个层面的东西。
>
> 可以这样理解：
>
> ```
> Singleton_04
> │
> ├── static class SingletonHolder
> │       │

> │                              │
> │                              ↓
> │                           Object①
> │
> └── getInstance()
> ```
>
> 真正的单例对象是：
>
> ```
> Object①
> ```
>
> 而不是 `SingletonHolder`。
>

### （5） 双重检查懒汉式单例模式

```java
//双重检查锁单例(懒汉模式)
public class Singleton_05 {

    // 静态成员变量：整个类共享这一份 instance 引用
    // volatile 有两个重要作用：
    // 1. 保证一个线程对 instance 的修改能够被其他线程及时看到
    // 2. 禁止 JVM 对 instance = new Singleton_05() 相关的内存操作进行
    //    某些可能导致“对象尚未完全初始化就被其他线程看到”的重排序
    // 初始值为 null，说明此时还没有创建 Singleton_05 对象
    //禁止与对象发布相关的危险重排序，保证其他线程不会通过一个已经变成非 null 的引用看到一个尚未完成初始化的对象。
    private static volatile Singleton_05 instance;

    // 私有构造方法：禁止外部通过 new 创建 Singleton_05 对象
    private Singleton_05() {
    }

    // 对外提供唯一的实例获取入口
    public static Singleton_05 getInstance() {
        // 第一次检查：
        // 如果 instance 已经创建好了，就直接返回
        // 绝大多数情况下，单例对象已经存在，
        // 因此不需要进入 synchronized，减少加锁开销
        if (null != instance) {
            return instance;
        }
        // 第一次检查发现 instance == null，
        // 说明单例可能还没有创建
        // 对 Singleton_05.class 加锁，
        // 保证同一时刻只有一个线程能够进入下面的代码
        synchronized (Singleton_05.class) {
            // 第二次检查：
            // 线程进入锁之前，可能已经有其他线程创建好了 instance
            // 所以进入 synchronized 后必须再次检查
            if (null == instance) {
                // 确认还没有创建对象，
                // 当前线程负责创建唯一的 Singleton_05 对象
                instance = new Singleton_05();
            }
        }
        // 返回已经创建好的单例对象
        return instance;
    }
}
```

释义

> ### 2. 先不要急着理解 `volatile`
>
> 先把这段代码的整体逻辑搞懂。
>
> 核心其实只有：
>
> ```java
> if (instance == null) {
>     synchronized (Singleton_05.class) {
>         if (instance == null) {
>             instance = new Singleton_05();
>         }
>     }
> }
> return instance;
> ```
>
> 它为什么要这么写？
>
> 因为作者想同时达到三个目标：
>
> 1. **懒加载**
> 2. **线程安全**
> 3. **不要让每一次 `getInstance()` 都加锁**
>
> 这三个目标结合起来，就产生了 DCL。
>
> ------
>
> ### 3. 如果不用 DCL，会怎么样？
>
> 先回到你前面的 `Singleton_02`：
>
> ```java
> public static synchronized Singleton_02 getInstance() {
> 
>     if (instance == null) {
>         instance = new Singleton_02();
>     }
> 
>     return instance;
> }
> ```
>
> 这个非常简单。
>
> 第一次：
>
> ```
> instance == null
>       ↓
> 加锁
>       ↓
> new Singleton_02()
>       ↓
> Object①
> ```
>
> 以后：
>
> ```
> instance != null
>       ↓
> 依然进入 synchronized
>       ↓
> 判断
>       ↓
> return instance
> ```
>
> 也就是说：
>
> > **即使对象早就创建好了，每次调用 `getInstance()` 仍然需要进行同步。**
>
> 例如：
>
> ```
> Singleton_02.getInstance();
> Singleton_02.getInstance();
> Singleton_02.getInstance();
> Singleton_02.getInstance();
> ```
>
> 每一次都要经过：
>
> ```
> getInstance()
>     ↓
> synchronized
>     ↓
> 检查 instance
>     ↓
> return
> ```
>
> 这在高频调用的场景下可能产生不必要的同步开销。
>
> ------
>
> ### 4. DCL 的第一层检查就是为了解决这个问题
>
> 看看：
>
> ```
> if (null != instance) {
>     return instance;
> }
> ```
>
> 意思是：
>
> > **如果单例已经存在，就不要加锁了，直接返回。**
>
> 于是正常情况下：
>
> ```
> getInstance()
>      ↓
> instance != null
>      ↓
> return instance
> ```
>
> 根本不会执行：
>
> ```
> synchronized
> ```
>
> 所以：
>
> > **锁只用于解决“对象还没有创建”的情况。**
>
> ------
>
> ### 5. 那为什么还需要第二个 `if`？
>
> 这是 DCL 最关键的地方。
>
> 你可能会觉得：
>
> ```
> if (instance == null) {
> 
>     synchronized (Singleton_05.class) {
>         instance = new Singleton_05();
>     }
> }
> ```
>
> 不就够了吗？
>
> **不够。**
>
> 因为可能出现这种情况。
>
> 假设：
>
> ```
> instance == null
> ```
>
> 此时来了两个线程：
>
> ```
> 线程A                    线程B
> 
>   ↓                        ↓
> 检查 instance              检查 instance
>   ↓                        ↓
> null                       null
>   ↓                        ↓
> 进入 synchronized          等待锁
>   ↓
> 创建 Object①
>   ↓
> instance → Object①
>   ↓
> 释放锁
>                            ↓
>                        获得锁
>                            ↓
>                        如果没有第二次检查
>                            ↓
>                        new Object②
> ```
>
> 那么就产生：
>
> ```
> Object①
> Object②
> ```
>
> 单例就被破坏了。
>
> ------
>
> ### 6. 所以必须第二次检查
>
> 因此：
>
> ```java
> synchronized (Singleton_05.class) {
> 
>     if (null == instance) {
>         instance = new Singleton_05();
>     }
> }
> ```
>
> 第二次：
>
> ```
> if (null == instance)
> ```
>
> 是非常关键的。
>
> 还是刚才那个场景：
>
> ```
> 线程A                         线程B
> 
> 第一次检查                    第一次检查
> instance == null             instance == null
>      ↓                            ↓
> 进入锁                       等待锁
>      ↓
> new Object①
>      ↓
> instance → Object①
>      ↓
> 释放锁
>                               ↓
>                          获得锁
>                               ↓
>                     第二次检查 instance
>                               ↓
>                        instance != null
>                               ↓
>                          不再 new
> ```
>
> 于是最终只有：
>
> ```
> Object①
> ```
>
> 这就是：
>
> > **Double-Checked Locking**
> >
> > **双重检查锁**
>
> ------
>
> ### 7. 为什么叫“双重检查”？
>
> 非常直观：
>
> ### 第一次检查
>
> ```
> if (null != instance)
> ```
>
> 在锁外。
>
> 目的：
>
> > **已经创建 → 直接返回 → 不加锁。**
>
> ------
>
> ### 第二次检查
>
> ```
> if (null == instance)
> ```
>
> 在锁里面。
>
> 目的：
>
> > **多个线程同时发现 null 后，最终只有真正拿到锁且再次发现 null 的那个线程负责创建对象。**
>
> 所以：
>
> ```
>         getInstance()
>              │
>              ↓
>        第一次检查
>        instance != null ?
>           /       \
>         是         否
>         ↓          ↓
>       return    synchronized
>                    │
>                    ↓
>               第二次检查
>               instance == null ?
>                  /       \
>                否         是
>                ↓          ↓
>              return      new
>                           ↓
>                        Object①
> ```
>
> 这就是整个 DCL 的核心。
>
> ------
>
> ### 8. 那 `synchronized (Singleton_05.class)` 锁的是什么？
>
> 这里：
>
> ```
> synchronized (Singleton_05.class)
> ```
>
> 锁的是：
>
> > **`Singleton_05.class` 这个 Class 对象。**
>
> 也就是类级别的锁。
>
> 你前面刚刚学过：
>
> ```
> public static synchronized Singleton_02 getInstance()
> ```
>
> 实际上相当于：
>
> ```
> synchronized (Singleton_02.class)
> ```
>
> 所以这里本质上是同一种锁。
>
> ------
>
> ### 9. 为什么这里必须锁 `Singleton_05.class`？
>
> 因为：
>
> ```
> getInstance()
> ```
>
> 是：
>
> ```
> static
> ```
>
> 它还没有任何 `Singleton_05` 对象。
>
> 所以你不能：
>
> ```
> synchronized (this)
> ```
>
> 因为此时可能根本没有 `this` 对象。
>
> 所以要找一个**所有线程都能共同访问的锁对象**：
>
> ```
> Singleton_05.class
> ```
>
> 所有线程看到的都是同一个 `Class` 对象：
>
> ```
> 线程A ──┐
> 线程B ──┼──→ Singleton_05.class
> 线程C ──┤
> 线程D ──┘
> ```
>
> 因此它们可以互相排斥。
>
> ------
>
> ### 10. 现在来到最重要的 `volatile`
>
> 代码：
>
> ```
> private static volatile Singleton_05 instance;
> ```
>
> 如果你只把 `volatile` 理解成：
>
> > “保证线程之间看到最新值。”
>
> 还不够。
>
> 在 DCL 中，`volatile` 有一个非常重要的作用：
>
> > **禁止与对象发布相关的危险重排序，保证其他线程不会通过一个已经变成非 `null` 的引用看到一个尚未完成初始化的对象。**
>
> 这是 DCL 必须使用 `volatile` 的核心原因。
>
> ------
>
> ### 11. 为什么 `new Singleton_05()` 会有这个问题？
>
> 你写：
>
> ```
> instance = new Singleton_05();
> ```
>
> 从程序员角度看，好像就是一个动作：
>
> ```
> 创建对象
>    ↓
> 赋给 instance
> ```
>
> 但 JVM 执行对象创建时，从抽象层面可以理解为几个步骤：
>
> ```
> ① 分配内存
>       ↓
> ② 初始化对象
>       ↓
> ③ instance 指向这块内存
> ```
>
> 正常顺序：
>
> ```
> 分配内存
>   ↓
> 初始化 Singleton_05
>   ↓
> instance → 对象
> ```
>
> 但是在没有正确内存语义约束的情况下，编译器/JVM 可能对这些操作进行允许的重排序。
>
> 可能出现：
>
> ```
> ① 分配内存
>       ↓
> ③ instance 指向内存
>       ↓
> ② 初始化对象
> ```
>
> 于是另一个线程可能看到：
>
> ```
> instance != null
> ```
>
> 但是对象还没有完全初始化完成。
>
> 这就是 DCL 中经典的：
>
> > **对象半初始化 / 不安全发布问题。**
>
> ------
>
> ### 12. `volatile` 在这里解决什么？
>
> 加上：
>
> ```
> private static volatile Singleton_05 instance;
> ```
>
> 以后，对 `instance` 的读写具有更强的内存可见性和顺序保证。
>
> 因此可以保证：
>
> ```
> 对象初始化完成
>       ↓
> instance 发布
> ```
>
> 不会因为允许的重排序而让其他线程看到：
>
> ```
> instance != null
>       ↓
> 但是对象还没初始化完
> ```
>
> 所以经典 DCL 写法必须是：
>
> ```
> private static volatile Singleton_05 instance;
> ```
>
> 而不是：
>
> ```
> private static Singleton_05 instance;
> ```
>
> ------
>
> ### 13. 所以整个 DCL 是三个知识点组合
>
> 你可以把它拆成：
>
> ```
>              DCL 单例
>                  │
>        ┌─────────┼─────────┐
>        ↓         ↓         ↓
>     static    synchronized volatile
>        │         │          │
>        ↓         ↓          ↓
>  类级别共享   保证互斥    安全发布/
>  instance    防止重复创建  防止危险重排序
> ```
>
> 再加上：
>
> ```
> private Singleton_05() {}
> ```
>
> 解决：
>
> > 外部不能 `new`
>
> 所以整个单例成立。
>

>
> ### 14. 完整执行流程
>
> 假设程序第一次调用：
>
> ```

> ```
>
> 初始状态：
>
> ```
> instance → null
> ```
>
> 执行：
>
> ```
> if (null != instance)
> ```
>
> 结果：
>
> ```
> null != null
> ↓
> false
> ```
>
> 进入：
>
> ```

> ```
>
> 然后第二次检查：
>
> ```

> ```
>
> 结果：
>
> ```

> ↓

> ```
>
> 于是：
>
> ```
> instance = new Singleton_05();
> ```
>
> 最终：
>
> ```
> instance ───────→ Object①
> ```
>
> 返回：
>
> ```
> s1 ─────────────→ Object①
> ```
>
> ------
>
> ### 15. 第二次调用
>
> ```
> Singleton_05 s2 = Singleton_05.getInstance();
> ```
>
> 第一次检查：
>
> ```
> if (null != instance)
> ```
>
> 现在：
>

> ```
>
> 所以：
>
> ```
> true
> ```
>
> 直接：

> ```
>
> 于是：
>
> ```

> ```

> ### 17. 多线程情况下为什么不会创建两个？
>
> 假设：
>
> ```
> instance == null
> ```
>
> 同时来了线程 A、B、C。
>
> ### 第一阶段：第一次检查
>
> ```
> 线程A → instance == null
> 线程B → instance == null
> 线程C → instance == null
> ```
>
> 三个人都可能进入 `synchronized`。
>
> ------
>
> ### 第二阶段：竞争锁
>
> ```
> 线程A → 获得 Singleton_05.class 锁
> 线程B → 等待
> 线程C → 等待
> ```
>
> A：
>
> ```
> 第二次检查
> instance == null
>       ↓
> new Object①
>       ↓
> instance → Object①
>       ↓
> 释放锁
> ```
>
> B 获得锁：
>
> ```
> 第二次检查
> instance == null ?
>       ↓
> false
>       ↓
> 不创建
>       ↓
> 释放锁
> ```
>
> C 同样：
>
> ```
> instance != null
>       ↓
> 不创建
> ```
>
> 最终：
>
> ```
>              Object①
>              ↑  ↑  ↑
>              │  │  │
>              A  B  C
> ```
>
> 只有一个实例。
>
> ------
>
> ### 18. 为什么第一次检查放锁外，第二次检查放锁内？
>
> 这是 DCL 最值得你记住的一句话：
>
> > **第一次检查负责性能，第二次检查负责正确性。**
>
> ### 第一次检查
>
> ```
> if (instance != null) {
>     return instance;
> }
> ```
>
> 解决：
>
> > **对象已经存在时，不要每次都加锁。**
>
> ------
>
> ### 第二次检查
>
> ```
> synchronized (...) {
>     if (instance == null) {
>         instance = new Singleton_05();
>     }
> }
> ```
>
> 解决：
>
> > **多个线程同时进入等待区时，最终只有一个线程创建对象。**
>
> ------
>
> ### 19. 和 Singleton_02、Singleton_03、Singleton_04 放在一起
>
> 现在你已经学了四种非常重要的实现：
>
> | 版本           | 类型              | 懒加载 | 线程安全 | 每次获取加锁 |
> | -------------- | ----------------- | ------ | -------- | ------------ |
> | `Singleton_02` | synchronized 懒汉 | ✅      | ✅        | ✅            |
> | `Singleton_03` | 饿汉式            | ❌      | ✅        | ❌            |
> | `Singleton_04` | 静态内部类        | ✅      | ✅        | ❌            |
> | `Singleton_05` | DCL               | ✅      | ✅        | ❌            |
>
> 所以从**实际工程角度**来看：
>
> ```
> Singleton_02
>     ↓
> 简单，但是每次 synchronized
>     ↓
> Singleton_03
>     ↓
> 简单、线程安全，但不是懒加载
>     ↓
> Singleton_04
>     ↓
> 懒加载 + 线程安全 + 简单
>     ↓
> Singleton_05
>     ↓
> 懒加载 + 线程安全 + 减少锁竞争
>        ↓
> 但实现复杂，需要理解 volatile/JMM
> ```
>
> 这也解释了一个很重要的工程结论：
>
> > **DCL 并不是“单例模式的最终答案”。**
>
> 如果只是为了写一个 Java 单例，`Singleton_04` 的 Holder 模式通常已经非常漂亮。
>
> 而 `Singleton_05` 的真正学习价值在于：
>
> > **它是一个非常经典的案例，用来理解 `synchronized`、`volatile`、可见性、指令重排序、安全发布以及 Java 内存模型。**
>
> ------
>
> ## 最后把 `Singleton_05` 压缩成一句面试答案
>
> 如果面试官问：
>
> > **“介绍一下双重检查锁单例。”**
>
> 你可以这样答：
>
> > 双重检查锁是一种懒加载的线程安全单例实现。它在 `instance` 第一次检查不为 `null` 时直接返回，避免每次获取实例都进入同步代码；如果第一次检查发现为空，则通过 `synchronized` 保证并发情况下只有一个线程能够创建实例，并在锁内部再次检查 `instance`，防止多个线程重复创建。`instance` 必须使用 `volatile`，用于保证可见性和禁止与对象发布相关的危险重排序，从而避免其他线程看到尚未完全初始化的对象。

### （6）CAS 实现的懒汉式单例模式

```java
import java.util.concurrent.atomic.AtomicReference;

public class Singleton_06 {

    // AtomicReference 是一个“原子引用变量”
    // 可以把它理解成：
    //     INSTANCE 里面存放的是一个 Singleton_06 对象的引用
    // 它提供了线程安全的：
    //     get()              获取引用
    //     set()              修改引用
    //     compareAndSet()    CAS：比较并更新
    // 初始值为 null，表示目前还没有创建单例对象。
    private static final AtomicReference<Singleton_06> INSTANCE =
            new AtomicReference<>();


    // 这个变量实际上没有被使用，是多余的。
    // 当前代码真正保存单例对象引用的是上面的 INSTANCE。
    // 所以这个变量可以直接删除。
    private static Singleton_06 instance;


    // 私有构造方法：
    // 禁止外部直接 new Singleton_06()
    // 例如：
    // Singleton_06 s = new Singleton_06(); // 编译错误
    private Singleton_06() {
    }


    // 对外提供唯一的实例获取入口。
    // static：
    // 不需要创建 Singleton_06 对象，就可以调用：
    // Singleton_06.getInstance()
    // final：
    // 表示这个方法不能被子类重写。
    public static final Singleton_06 getInstance() {

        // for(;;) 就是一个无限循环：
        // for (;;) {
        //     ...
        // }
        // 等价于：
        // while (true) {
        //     ...
        // }
        // 不过当前代码实际上每次都会 return，
        // 所以这个无限循环并没有发挥作用。
        for (;;) {

            // 从 AtomicReference 中获取当前保存的对象引用。
            // 如果还没有创建单例：
            //     instance == null
            // 如果已经创建：
            //     instance == 某一个 Singleton_06 对象
            Singleton_06 instance = INSTANCE.get();


            // 如果已经存在单例对象，
            // 直接把这个对象返回。
            // 这意味着已经初始化完成之后，
            // 后续调用不需要创建新对象。
            if (instance != null) {
                return instance;
            }


            // CAS（Compare And Set）
            // compareAndSet(expectedValue, newValue)      
            // 意思是：            
            //     如果 INSTANCE 当前的值仍然是 null，
            //     那么就把它修改成新创建的 Singleton_06 对象。            
            //     如果 INSTANCE 已经不是 null，
            //     那么什么都不修改。            
            // 整个“比较 + 修改”过程是原子的。            
            // 这里：            
            //     null
            //       ↓
            //     new Singleton_06()            
            // 只有一个线程能够成功把 null 替换成自己的对象。
            INSTANCE.compareAndSet(
                    null,
                    instance = new Singleton_06()
            );


            // 无论当前线程自己的 CAS 成功还是失败，
            // 最终都重新从 INSTANCE 中获取真正保存的对象。          
            // CAS 成功：
            //     返回当前线程创建的对象            
            // CAS 失败：
            //     说明其他线程已经抢先创建并放入了对象
            //     返回其他线程创建的对象
            return INSTANCE.get();
        }
    }


    public static void main(String[] args) {

        // 第一次获取单例对象
        Singleton_06 s1 = Singleton_06.getInstance();

        // 第二次获取单例对象
        Singleton_06 s2 = Singleton_06.getInstance();

        System.out.println(s1);
        System.out.println(s2);

        // 判断两个引用是否指向同一个对象
        System.out.println(s1 == s2);
    }
}
```

```java
public class Singleton_06 {
    // 原子引用，保存唯一的 Singleton_06 对象引用
    private static final AtomicReference<Singleton_06> INSTANCE =
            new AtomicReference<>();

    // 私有构造方法，禁止外部 new
    private Singleton_06() {
    }

    // 获取单例对象
    public static Singleton_06 getInstance() {
        // 第一次检查
        Singleton_06 instance = INSTANCE.get();
        // 已经创建，直接返回
        if (instance != null) {
            return instance;
        }
        // CAS：
        // 如果当前仍然是 null，
        // 就把新对象设置进去
        INSTANCE.compareAndSet(
                null,
                new Singleton_06()
        );
        // 无论 CAS 成功还是失败，
        // 最终都返回 INSTANCE 中真正保存的对象
        return INSTANCE.get();
    }
}
```

释义：

> ### 一、先抓住 `AtomicReference` 是什么
>
> 你之前学习 `static` 的时候，可以把：
>
> ```
> private static Singleton_05 instance;
> ```
>
> 理解成：
>
> ```
> Singleton_05.class
>        │
>        ▼
>    instance
>        │
>        ▼
>    Singleton_05对象
> ```
>
> 而现在：
>
> ```
> private static final AtomicReference<Singleton_06> INSTANCE
>         = new AtomicReference<>();
> ```
>
> 变成：
>
> ```
> Singleton_06.class
>        │
>        ▼
>     INSTANCE
>        │
>        ▼
> AtomicReference对象
>        │
>        ▼
> Singleton_06对象
> ```
>
> 所以这里实际上多了一层。
>
> ------
>
> ### 二、`AtomicReference` 到底解决什么问题？
>
> `AtomicReference<T>` 可以理解成：
>
> > **一个能够对“对象引用”进行原子操作的容器。**
>
> 例如：
>
> ```
> AtomicReference<String> ref = new AtomicReference<>();
> 
> ref.set("Hello");
> 
> String value = ref.get();
> ```
>
> 这里：
>
> ```
> ref.get()
> ```
>
> 就是获取引用。
>
> ```
> ref.set(...)
> ```
>
> 就是修改引用。
>
> 最关键的是：
>
> ```
> ref.compareAndSet(...)
> ```
>
> 也就是 **CAS**。
>
> ------
>
> ### 三、什么是 CAS？
>
> CAS 是：
>
> > **Compare And Set**
>
> 也就是：
>
> > **比较并设置。**
>
> 例如：
>
> ```
> INSTANCE.compareAndSet(null, new Singleton_06());
> ```
>
> 可以理解成：
>
> ```
> 如果 INSTANCE 现在是 null
>         ↓
>     那么设置成新对象
> 
> 如果 INSTANCE 现在不是 null
>         ↓
>     什么都不做
> ```
>
> 关键是：
>
> > **“检查”和“修改”是一个原子操作。**
>
> 这就是它能够处理并发问题的核心。
>
> ------
>
> ### 四、为什么 CAS 能实现单例？
>
> 假设现在有三个线程：
>
> ```
> 线程 A
> 线程 B
> 线程 C
> ```
>
> 同时执行：
>
> ```
> Singleton_06.getInstance();
> ```
>
> 刚开始：
>
> ```
> INSTANCE
>    │
>    ▼
>  null
> ```
>
> 三个线程执行：
>
> ```
> Singleton_06 instance = INSTANCE.get();
> ```
>
> 于是它们都可能得到：
>
> ```
> A → null
> B → null
> C → null
> ```
>
> 于是三个线程都准备执行：
>
> ```
> INSTANCE.compareAndSet(
>     null,
>     new Singleton_06()
> );
> ```
>
> 假设线程 A 最先执行 CAS。
>
> ------
>
> ### 第一步：线程 A
>
> 线程 A：
>
> ```
> INSTANCE == null
> ```
>
> 于是：
>
> ```
> compareAndSet(null, Object_A)
> ```
>
> 成功。
>
> 现在：
>
> ```
> INSTANCE
>    │
>    ▼
> Object_A
> ```
>
> ------
>
> ## 第二步：线程 B
>
> 线程 B 之前也看到过：
>
> ```
> INSTANCE == null
> ```
>
> 所以它也创建了：
>
> ```
> Object_B
> ```
>
> 然后执行：
>
> ```
> compareAndSet(null, Object_B)
> ```
>
> 但是此时：
>
> ```
> INSTANCE == Object_A
> ```
>
> 已经不是 `null` 了。
>
> 所以：
>
> ```
> CAS失败
> ```
>
> `Object_B` 不会被放入 `INSTANCE`。
>
> ------
>
> ## 第三步：线程 C
>
> 同理：
>
> ```
> Object_C
> ```
>
> 可能也被创建出来。
>
> 然后：
>
> ```
> compareAndSet(null, Object_C)
> ```
>
> 失败。
>
> 最终：
>
> ```
> INSTANCE
>    │
>    ▼
> Object_A
> ```
>
> ------
>
> ### 五、这里有一个非常重要的细节
>
> 这也是你学习 CAS 时一定要注意的。
>
> **CAS 单例并不保证并发情况下只执行一次 `new Singleton_06()`。**
>
> 例如：
>
> ```
> 线程A → new Singleton_06() → Object_A
> 线程B → new Singleton_06() → Object_B
> 线程C → new Singleton_06() → Object_C
> ```
>
> 三个对象都有可能被创建。
>
> 但是：
>
> ```
> 线程A → CAS成功 → INSTANCE = Object_A
> 
> 线程B → CAS失败 → Object_B没有发布
> 线程C → CAS失败 → Object_C没有发布
> ```
>
> 最终：
>
> ```
> INSTANCE
>    │
>    ▼
> Object_A
> ```
>
> 所以应该准确地说：
>
> > **CAS 保证只有一个对象能够成功成为最终发布的单例实例，但不保证并发竞争过程中只执行一次构造方法。**
>
> 这和 `synchronized` 的实现有一点区别。
>
> ------
>
> #### 六、和 Singleton_05 的 DCL 对比
>
> 你上一版：
>
> ```
> private static volatile Singleton_05 instance;
> 
> public static Singleton_05 getInstance() {
> 
>     if (instance != null) {
>         return instance;
>     }
> 
>     synchronized (Singleton_05.class) {
> 
>         if (instance == null) {
>             instance = new Singleton_05();
>         }
>     }
> 
>     return instance;
> }
> ```
>
> 核心思想是：
>
> ```
> 第一次检查
>     ↓
> instance == null？
>     ↓
> 进入 synchronized
>     ↓
> 第二次检查
>     ↓
> 还是 null？
>     ↓
> new
> ```
>
> 所以它依靠：
>
> ```
> synchronized
> ```
>
> 保证：
>
> > 同一时刻只有一个线程能够执行创建代码。
>
> ------
>
> 而 Singleton_06 是：
>
> ```
> 多个线程可以同时尝试
>         ↓
>       CAS
>         ↓
> 谁先成功谁赢
>         ↓
> 其他线程失败
> ```
>
> 也就是：
>
> ```
> DCL：
> 
> 锁竞争
>  ↓
> 一个线程进入
>  ↓
> 创建对象
>  ↓
> 其他线程等待
> 
> 
> CAS：
> 
> 多个线程竞争
>  ↓
> 同时尝试 CAS
>  ↓
> 一个成功
>  ↓
> 其他失败
> ```
>
> ------
>
> ### 七、你这段代码实际上可以简化
>
> 你现在有：
>
> ```
> for (;;) {
> 
>     Singleton_06 instance = INSTANCE.get();
> 
>     if(instance != null) return instance;
> 
>     INSTANCE.compareAndSet(null, instance = new Singleton_06());
> 
>     return INSTANCE.get();
> }
> ```
>
> 实际上：
>
> ```
> return
> ```
>
> 已经在第一次循环里面了。
>
> 所以：
>
> ```
> for (;;) {
> ```
>
> 完全没有必要。
>
> 可以改成：
>
> ```
> public static Singleton_06 getInstance() {
> 
>     Singleton_06 instance = INSTANCE.get();
> 
>     if (instance != null) {
>         return instance;
>     }
> 
>     INSTANCE.compareAndSet(
>             null,
>             new Singleton_06()
>     );
> 
>     return INSTANCE.get();
> }
> ```
>
> 这样逻辑就非常清楚了。
>
> 甚至把无用的：
>
> ```
> private static Singleton_06 instance;
> ```
>
> 也删掉。
>
> 最终：
>
> ```java
> public class Singleton_06 {
> 
>     // 原子引用，保存唯一的 Singleton_06 对象引用
>     private static final AtomicReference<Singleton_06> INSTANCE =
>             new AtomicReference<>();
> 
>     // 私有构造方法，禁止外部 new
>     private Singleton_06() {
>     }
> 
>     // 获取单例对象
>     public static Singleton_06 getInstance() {
> 
>         // 第一次检查
>         Singleton_06 instance = INSTANCE.get();
> 
>         // 已经创建，直接返回
>         if (instance != null) {
>             return instance;
>         }
> 
>         // CAS：
>         // 如果当前仍然是 null，
>         // 就把新对象设置进去
>         INSTANCE.compareAndSet(
>                 null,
>                 new Singleton_06()
>         );
> 
>         // 无论 CAS 成功还是失败，
>         // 最终都返回 INSTANCE 中真正保存的对象
>         return INSTANCE.get();
>     }
> }
> ```
>
> 这个版本更适合你现在学习。

>

> ## 1. 普通变量和 `AtomicReference` 的区别
>
> 普通写法：
>
> ```
> private static Singleton_06 instance;
> ```
>
> 相当于：
>
> ```
> instance
>    │
>    ▼
> Singleton_06对象
> ```
>
> 它只能保存一个 `Singleton_06` 对象的引用。
>
> 而：
>
> ```
> AtomicReference<Singleton_06> INSTANCE
> ```
>
> 相当于：
>
> ```
> INSTANCE
>    │
>    ▼
> ┌──────────────────────┐
> │ AtomicReference      │
> │                      │
> │ value ───────────────┼──────► Singleton_06对象
> └──────────────────────┘
> ```
>
> `AtomicReference` 自己也是一个**对象**，它内部有一个位置，用来保存：
>
> ```
> Singleton_06
> ```
>
> 类型的引用。
>
> 所以：
>
> ```
> AtomicReference<Singleton_06>
> ```
>
> 可以粗略理解成：
>
> > **“一个能够线程安全地保存和修改 `Singleton_06` 引用的盒子。”**

### （7）枚举单例模式

```java
/**
 * 枚举单例模式
 * Java 会保证一个枚举类型中的每一个枚举常量在整个 JVM 中只有一个实例。
 */
public enum Singleton_07 {

    // 枚举常量 INSTANCE
    // INSTANCE 本身就是 Singleton_07 类型的唯一对象。
    // 可以理解为
    // Singleton_07 INSTANCE = new Singleton_07();
    // 但这个对象的创建和管理由 JVM / Java 的枚举机制负责，
    // 我们不能自己 new Singleton_07()。
    INSTANCE;
    // 单例对象的普通实例方法
    public void test() {
        System.out.println("hi~");
    }
}

```

释义：

> ### 先把代码完整注释一下
>
> ```java
> /**
>  * 枚举单例模式
>  *
>  * Java 会保证一个枚举类型中的每一个枚举常量在整个 JVM 中只有一个实例。
>  */
> public enum Singleton_07 {
> 
>     // 枚举常量 INSTANCE
>     //
>     // INSTANCE 本身就是 Singleton_07 类型的唯一对象。
>     // 可以理解为：
>     //
>     // Singleton_07 INSTANCE = new Singleton_07();
>     //
>     // 但这个对象的创建和管理由 JVM / Java 的枚举机制负责，
>     // 我们不能自己 new Singleton_07()。
>     INSTANCE;
> 
>     // 单例对象的普通实例方法
>     public void test() {
>         System.out.println("hi~");
>     }
> }
> ```
>
> 使用的时候：
>
> ```java
> public class Test {
> 
>     public static void main(String[] args) {
> 
>         // 获取枚举单例 INSTANCE
>         Singleton_07 s1 = Singleton_07.INSTANCE;
> 
>         // 再次获取 INSTANCE
>         Singleton_07 s2 = Singleton_07.INSTANCE;
> 
>         // 两个引用指向同一个对象
>         System.out.println(s1 == s2); // true
> 
>         // 调用单例对象的方法
>         s1.test(); // hi~
>     }
> }
> ```
>
> ------
>
> ### 一、最重要的一点：`INSTANCE` 到底是什么？
>
> 你可以把：
>
> ```
> public enum Singleton_07 {
>     INSTANCE;
> }
> ```
>
> 理解成：
>
> > 定义了一个叫 `Singleton_07` 的枚举类型，而这个枚举类型里面只有一个枚举常量：`INSTANCE`。
>
> 而**枚举常量本身就是对象**。
>
> 所以：
>
> ```
> Singleton_07.INSTANCE
> ```
>
> 得到的不是一个普通的字符串、数字或者标记，而是一个真正的：
>
> ```
> Singleton_07 对象
> ```
>
> 可以简单画成：
>
> ```
> Singleton_07
>       │
>       │ 唯一的枚举常量
>       ▼
>    INSTANCE
>       │
>       ▼
>  Singleton_07对象①
> ```
>
> 因此：
>
> ```
> Singleton_07 s1 = Singleton_07.INSTANCE;
> Singleton_07 s2 = Singleton_07.INSTANCE;
> ```
>
> 实际上就是：
>
> ```
> s1 ─────┐
>         ├──────> Singleton_07对象①
> s2 ─────┘
> ```
>
> 所以：
>
> ```
> s1 == s2
> ```
>
> 结果就是：
>
> ```
> true
> ```
>
> ------
>
> ### 二、它为什么天然就是单例？
>
> 你前面学的几种单例，基本都在想办法解决两个问题：
>
> ### 问题 1：怎么禁止别人 `new`？
>
> 比如：
>
> ```
> private Singleton_05() {
> }
> ```
>
> 让外部：
>
> ```
> new Singleton_05();
> ```
>
> 直接报错。
>
> ------
>
> ### 问题 2：怎么保证只有一个对象？
>
> 例如 DCL：
>
> ```
> private static volatile Singleton_05 instance;
> ```
>
> 然后通过：
>
> ```
> synchronized
> ```
>
> - 两次检查：
>
> ```
> if (instance == null) {
>     synchronized (...) {
>         if (instance == null) {
>             instance = new Singleton_05();
>         }
>     }
> }
> ```
>
> 来保证只有一个实例。
>
> ------
>
> 而**枚举单例不需要我们自己实现这些逻辑**。
>
> Java 的枚举机制已经帮你解决了：
>
> ```
> 不能随便 new
>       ↓
> 枚举对象由 JVM / Java 枚举机制创建
>       ↓
> 每个枚举常量只存在一个实例
>       ↓
> INSTANCE 就是唯一实例
> ```
>
> 所以代码非常简单：
>
> ```
> public enum Singleton_07 {
>     INSTANCE;
> }
> ```
>
> 就已经完成了单例的核心要求。
>
> ------
>
> ### 三、为什么不能 `new Singleton_07()`？
>
> 这是枚举非常重要的一个特性。
>
> 你不能写：
>
> ```
> Singleton_07 s = new Singleton_07(); // ❌
> ```
>
> 编译器会直接拒绝。
>
> 枚举类型的实例不能由程序员通过普通 `new` 创建。
>
> 也就是说：
>
> ```
> public enum Singleton_07 {
>     INSTANCE;
> }
> ```
>
> 中的：
>
> ```
> INSTANCE
> ```
>
> 是 Java 在枚举初始化过程中创建的。
>
> 而不是你自己：
>
> ```
> new Singleton_07();
> ```
>
> 创建的。
>
> ------
>
> ### 四、它和前面的 Singleton_03 有什么区别？
>
> 你前面学过：
>
> ```
> public class Singleton_03 {
> 
>     private static final Singleton_03 instance =
>             new Singleton_03();
> 
>     private Singleton_03() {
>     }
> 
>     public static Singleton_03 getInstance() {
>         return instance;
>     }
> }
> ```
>
> 这两个其实非常值得放在一起比较。
>
> ### Singleton_03：饿汉式
>
> ```
> private static final Singleton_03 instance =
>         new Singleton_03();
> ```
>
> 我们自己写：
>
> ```
> new Singleton_03()
> ```
>
> 然后通过：
>
> ```
> private static final
> ```
>
> 保存唯一实例。
>
> ------
>
> ### Singleton_07：枚举单例
>
> ```
> public enum Singleton_07 {
>     INSTANCE;
> }
> ```
>
> 我们直接声明：
>
> ```
> INSTANCE
> ```
>
> Java 的枚举机制负责实例创建和唯一性。
>
> 所以可以理解成：
>
> ```
> 普通饿汉式
> 
> 我们自己：
>     new Singleton_03()
>          ↓
>     static final
>          ↓
>     唯一实例
> 
> 
> 枚举单例
> 
> Java 枚举机制：
>     创建 INSTANCE
>          ↓
>     保证 INSTANCE 唯一
>          ↓
>     Singleton_07.INSTANCE
> ```
>
> ------
>
> ### 五、它是懒汉式还是饿汉式？
>
> 这里要稍微严谨一点。
>
> 你前面已经总结出了：
>
> > **懒汉式/饿汉式描述的是对象什么时候创建。**
>
> 对于枚举：
>
> ```
> public enum Singleton_07 {
>     INSTANCE;
> }
> ```
>
> `INSTANCE` 属于枚举常量，它会在**枚举类初始化的时候创建**。
>
> 所以从单例模式的分类角度，通常可以理解为：
>
> > **枚举单例不是传统意义上的懒汉式，而是依赖枚举类初始化机制创建实例。**
>
> 你可以和前面几个版本这样记：
>
> | 版本           | 实现方式          | 创建机制               |
> | -------------- | ----------------- | ---------------------- |
> | `Singleton_01` | 普通懒汉          | 第一次 `getInstance()` |
> | `Singleton_02` | synchronized 懒汉 | 第一次 `getInstance()` |
> | `Singleton_03` | 饿汉式            | 类初始化               |
> | `Singleton_04` | 静态内部类        | Holder 初始化          |
> | `Singleton_05` | DCL               | 第一次 `getInstance()` |
> | `Singleton_06` | CAS               | 第一次 `getInstance()` |
> | `Singleton_07` | **枚举单例**      | **枚举类初始化**       |
>
> 所以你可以直接把它命名为：
>
> > **枚举单例模式（Enum Singleton）**
>
> 而不是“枚举懒汉式”。
>
> ------
>
> ### 六、为什么枚举单例这么受推崇？
>
> 这里是它真正厉害的地方。
>
> 你前面学 DCL 的时候，需要：
>
> ```
> private static volatile Singleton_05 instance;
> ```
>
> 然后：
>
> ```
> if (instance == null) {
>     synchronized (Singleton_05.class) {
>         if (instance == null) {
>             instance = new Singleton_05();
>         }
>     }
> }
> ```
>
> 需要考虑：
>
> - `synchronized`
> - `volatile`
> - 可见性
> - 指令重排序
> - 双重检查
> - 安全发布
>
> 而枚举：
>
> ```
> public enum Singleton_07 {
>     INSTANCE;
> }
> ```
>
> 这些都不需要你自己处理。
>
> ### 甚至连序列化问题都考虑到了
>
> 这是枚举单例非常重要的优势。
>
> 普通单例如果实现：
>
> ```
> Serializable
> ```
>
> 还需要额外考虑**反序列化可能产生新的对象**的问题。
>
> 而 Java 对枚举的序列化/反序列化有特殊机制，能够保证枚举常量的身份不会因为普通反序列化而产生一个新的枚举实例。
>
> 因此枚举单例通常被认为是非常可靠的单例实现。
>
> ------
>

>

> ```

>
> 所以：
>
> ```
> Singleton_07.INSTANCE
> ```
>

>
> ```
> Singleton_03.getInstance()
> ```
>
> 或者：
>
> ```
> Singleton_05.getInstance()
> ```

> **如果是面试，我建议你把 `Singleton_07` 记成一句话：**
>
> > **枚举单例利用 Java 枚举类型本身的实例唯一性来实现单例，不需要手动编写 `private` 构造方法、`getInstance()`、`synchronized` 或 `volatile`，同时枚举还具有良好的序列化安全性，因此是 Java 中一种非常可靠的单例实现方式。**
>
> 其中最核心的一句话就是：
>
> > **`INSTANCE` 不是一个“标记”，而就是唯一的 `Singleton_07` 对象。**

##### 枚举与单例枚举

> 可以有多个，而且这恰恰是 `enum` 最基本的用途之一。
>
> 比如：
>
> ```java
> public enum Season {
>     SPRING,
>     SUMMER,
>     AUTUMN,
>     WINTER
> }
> ```
>
> 这里就有 **4 个枚举常量**：
>
> ```
> Season
>  ├── SPRING  → Season 对象①
>  ├── SUMMER  → Season 对象②
>  ├── AUTUMN  → Season 对象③
>  └── WINTER  → Season 对象④
> ```
>
> 每一个枚举常量**都是一个对象**，而且每个常量在该枚举类型中都只有一个实例。
>
> ------
>
> ### 所以为什么单例只写一个 `INSTANCE`？
>
> 因为我们利用的是：
>
> ```
> public enum Singleton_07 {
>     INSTANCE;
> }
> ```
>
> 这里的：
>
> ```
> INSTANCE
> ```
>
> 是唯一的枚举常量。
>
> 因此：
>
> ```
> Singleton_07.INSTANCE
> ```
>
> 天然就只有一个对象。
>
> 如果你写成：
>
> ```
> public enum Singleton_07 {
>     INSTANCE,
>     INSTANCE2,
>     INSTANCE3;
> }
> ```
>
> 那么实际上就有 **3 个对象**：
>
> ```
> Singleton_07
>  ├── INSTANCE  → 对象①
>  ├── INSTANCE2 → 对象②
>  └── INSTANCE3 → 对象③
> ```
>
> 这时候它就**不是单例了**。
>
> ------
>
> ### 这也是理解枚举单例的关键
>
> 普通枚举：
>
> ```
> public enum Color {
>     RED,
>     GREEN,
>     BLUE
> }
> ```
>
> 意思是：
>
> > `Color` 这个类型允许存在三个固定的实例：`RED`、`GREEN`、`BLUE`。
>
> 而枚举单例：
>
> ```
> public enum Singleton_07 {
>     INSTANCE
> }
> ```
>
> 意思是：
>
> > `Singleton_07` 这个类型只允许存在一个固定实例：`INSTANCE`。
>
> 所以你可以把它记成：
>
> > **枚举不要求只有一个枚举常量；枚举单例才故意只定义一个枚举常量。**
>
> 还有一个很重要的点：**枚举常量不仅仅是“名字”，它们本身就是对象**。这也是为什么 `Singleton_07.INSTANCE.test()` 可以直接调用实例方法。

##### 枚举的应用

> 你可以把 `enum` 理解成一种**特殊的类**：它不仅可以有枚举常量，还可以有：
>
> - 成员变量
> - 构造方法
> - 实例方法
> - 静态方法
> - 内部类
> - 接口
> - 抽象方法
> - 每个枚举常量自己的实现
>
> 你最后问的“**每个枚举常量对应不同的方法实现**”，尤其重要，这实际上涉及**枚举 + 多态**。
>
> ------
>
> ### 1. enum 当然可以定义普通方法
>
> 例如：
>
> ```
> public enum Season {
> 
>     SPRING,
>     SUMMER,
>     AUTUMN,
>     WINTER;
> 
>     public void test() {//公共的方法
>         System.out.println("这是 Season 的 test 方法");
>     }
> }
> ```
>
> 使用：
>
> ```
> Season.SPRING.test();
> Season.SUMMER.test();
> ```
>
> 这里所有枚举常量都共享同一个 `test()` 方法。
>
> 可以理解为：
>
> ```
> Season
>    │
>    ├── SPRING ──┐
>    ├── SUMMER ──┤
>    ├── AUTUMN ──┼──> test()
>    └── WINTER ──┘
> ```
>
> 因为：
>
> ```
> SPRING
> ```
>
> 本质上是一个 `Season` 对象，所以它可以调用 `Season` 定义的实例方法。
>
> ------
>
> ### 2. enum 也可以有成员变量和构造方法
>
> 例如：
>
> ```
> public enum Season {
> 
>     SPRING("春天"),
>     SUMMER("夏天"),
>     AUTUMN("秋天"),
>     WINTER("冬天");
> 
>     private final String name;
> 
>     Season(String name) {
>         this.name = name;
>     }
> 
>     public void test() {
>         System.out.println(name);
>     }
> }
> ```
>
> 使用：
>
> ```
> Season.SPRING.test();
> Season.SUMMER.test();
> ```
>
> 输出：
>
> ```
> 春天
> 夏天
> ```
>
> 这里就能看到：
>
> ```
> SPRING("春天")
>        ↓
> 创建 SPRING 对象时
>        ↓
> 调用 Season(String name)
>        ↓
> name = "春天"
> ```
>
> 所以枚举常量实际上可以拥有**自己的状态**。
>
> ------
>
> ### 3. enum 当然也可以定义内部类
>
> 例如：
>
> ```java
> public enum Singleton_07 {
> 
>     INSTANCE;
> 
>     private Helper helper;
> 
>     public void test() {
>         helper = new Helper();
>         helper.sayHello();
>     }
> 
>     // 枚举内部定义的普通内部类
>     class Helper {
> 
>         public void sayHello() {
>             System.out.println("Hello");
>         }
>     }
> }
> ```
>
> 也可以定义 `static` 内部类：
>
> ```java
> public enum Singleton_07 {
> 
>     INSTANCE;
> 
>     public void test() {
>         Helper.sayHello();
>     }
> 
>     // 静态内部类
>     static class Helper {
> 
>         static void sayHello() {
>             System.out.println("Hello");
>         }
>     }
> }
> ```
>
> 所以：
>
> > **enum 本质上是一个特殊的类，因此类能够定义的大部分成员，enum 同样可以定义。**
>
> 当然，枚举有一些自己的语法规则，例如不能让外部通过普通 `new` 创建枚举实例。
>
> ------
>
> ### 4. 你最后问的重点：每个枚举常量能不能有自己的方法实现？
>
> **可以。**
>
> 而且这个功能非常经典。
>
> 例如我们定义一个操作：
>
> ```java
> public enum Operation {
> 
>     ADD {
>         @Override
>         public int calculate(int a, int b) {
>             return a + b;
>         }
>     },
> 
>     SUBTRACT {
>         @Override
>         public int calculate(int a, int b) {
>             return a - b;
>         }
>     },
> 
>     MULTIPLY {
>         @Override
>         public int calculate(int a, int b) {
>             return a * b;
>         }
>     },
> 
>     DIVIDE {
>         @Override
>         public int calculate(int a, int b) {
>             return a / b;
>         }
>     };
> 
>     public abstract int calculate(int a, int b);
> }
> ```
>
> 使用：
>
> ```java
> public class Test {
> 
>     public static void main(String[] args) {
> 
>         System.out.println(Operation.ADD.calculate(10, 5));
>         System.out.println(Operation.SUBTRACT.calculate(10, 5));
>         System.out.println(Operation.MULTIPLY.calculate(10, 5));
>         System.out.println(Operation.DIVIDE.calculate(10, 5));
>     }
> }
> ```
>
> 结果：
>
> ```
> 15
> 5
> 50
> 2
> ```
>
> ------
>
> ### 5. 这个语法第一次看可能非常奇怪
>
> 比如：
>
> ```java
> ADD {
>     @Override
>     public int calculate(int a, int b) {
>         return a + b;
>     }
> }
> ```
>
> 你可能会问：
>
> > `ADD` 后面的 `{}` 是什么？
>
> 这里不是普通的代码块。
>
> 它实际上表示：
>
> > **给 `ADD` 这个枚举常量提供自己的类体/实现。**
>
> 你可以暂时把它理解成：
>
> ```
> ADD
>  ↓
> 一个特殊的 Operation 实例
>  ↓
> 这个实例拥有自己的 calculate() 实现
> ```
>
> 同理：
>
> ```
> ADD       → calculate()：a + b
> SUBTRACT  → calculate()：a - b
> MULTIPLY  → calculate()：a × b
> DIVIDE    → calculate()：a ÷ b
> ```
>
> ------
>
> ### 6. 这实际上就是多态
>
> 这才是这个写法真正值得你理解的地方。
>
> 我们定义：
>
> ```
> public abstract int calculate(int a, int b);
> ```
>
> 说明：
>
> > `Operation` 要求每个具体枚举常量都必须实现 `calculate()`。
>
> 然后：
>
> ```
> ADD {
>     @Override
>     public int calculate(int a, int b) {
>         return a + b;
>     }
> }
> ```
>
> `ADD` 实现自己的版本。
>
> 而：
>
> ```
> SUBTRACT {
>     @Override
>     public int calculate(int a, int b) {
>         return a - b;
>     }
> }
> ```
>
> `SUBTRACT` 实现自己的版本。
>
> 这和你之前学的接口多态其实是一个思路：
>
> ```
> Operation
>     │
>     │ abstract calculate()
>     │
>     ├──── ADD
>     │       └── a + b
>     │
>     ├──── SUBTRACT
>     │       └── a - b
>     │
>     ├──── MULTIPLY
>     │       └── a × b
>     │
>     └──── DIVIDE
>             └── a ÷ b
> ```
>
> 所以你可以把它看成：
>
> > **枚举常量不仅可以代表一个固定对象，还可以让每个固定对象拥有不同的行为。**
>
> ------
>
> ### 7. 甚至每个枚举常量可以实现多个方法
>
> 完全可以。
>
> 例如：
>
> ```java
> public enum Animal {
> 
>     DOG {
> 
>         @Override
>         public void eat() {
>             System.out.println("狗吃狗粮");
>         }
> 
>         @Override
>         public void move() {
>             System.out.println("狗用四条腿跑");
>         }
>     },
> 
>     BIRD {
> 
>         @Override
>         public void eat() {
>             System.out.println("鸟吃虫子");
>         }
> 
>         @Override
>         public void move() {
>             System.out.println("鸟飞");
>         }
>     };
> 
>     public abstract void eat();
> 
>     public abstract void move();
> }
> ```
>
> 于是：
>
> ```
> Animal.DOG.eat();
> Animal.DOG.move();
> 
> Animal.BIRD.eat();
> Animal.BIRD.move();
> ```
>
> 分别执行不同实现。
>
> ------
>
> ### 8. 甚至可以混合“公共方法”和“各自实现的方法”
>
> 例如：
>
> ```java
> public enum Operation {
> 
>     ADD {
>         @Override
>         public int calculate(int a, int b) {
>             return a + b;
>         }
>     },
> 
>     SUBTRACT {
>         @Override
>         public int calculate(int a, int b) {
>             return a - b;
>         }
>     };
> 
>     // 抽象方法：每个枚举常量必须自己实现
>     public abstract int calculate(int a, int b);
> 
>     // 普通方法：所有枚举常量共享
>     public void hello() {
>         System.out.println("这是公共方法");
>     }
> }
> ```
>
> 那么：
>
> ```
> Operation.ADD.calculate(1, 2);
> Operation.ADD.hello();
> 
> Operation.SUBTRACT.calculate(1, 2);
> Operation.SUBTRACT.hello();
> ```
>
> 其中：
>
> ```
> calculate()
>     ↓
> 每个枚举常量自己实现
> 
> hello()
>     ↓
> 所有枚举常量共享
> ```
>
> ------
>
> ### 9. 回到你的 Singleton_07
>
> 你原来的：
>
> ```java
> public enum Singleton_07 {
>     INSTANCE;
> 
>     public void test() {
>         System.out.println("hi~");
>     }
> }
> ```
>
> 其实就是最简单的情况：
>
> ```
> Singleton_07
>       │
>       └── INSTANCE
>              │
>              └── test()
> ```
>
> 如果你愿意，甚至可以写：
>
> ```java
> public enum Singleton_07 {
> 
>     INSTANCE;
> 
>     public void test() {
>         System.out.println("hi~");
>     }
> 
>     public void hello() {
>         System.out.println("hello~");
>     }
> 
>     public static void staticTest() {
>         System.out.println("static test");
>     }
> 
>     static class Helper {
>         public void help() {
>             System.out.println("help");
>         }
>     }
> }
> ```
>
> 使用：
>
> ```
> Singleton_07.INSTANCE.test();
> Singleton_07.INSTANCE.hello();
> 
> Singleton_07.staticTest();
> 
> Singleton_07.Helper helper = new Singleton_07.Helper();
> helper.help();
> ```
>
> 所以你现在可以形成一个很重要的认识：
>
> > **`enum` 不是“只能写几个常量的特殊语法”，而是 Java 对“有限个固定实例”的一种类型定义。**
>
> 例如：
>
> ```
> public enum Color {
>     RED,
>     GREEN,
>     BLUE
> }
> ```
>
> 本质上是在说：
>
> > `Color` 这个类型，我规定它只能有 `RED / GREEN / BLUE` 这几个固定实例。
>
> 而：
>
> ```
> public enum Singleton_07 {
>     INSTANCE
> }
> ```
>
> 则是在说：
>
> > `Singleton_07` 这个类型，我规定它只有一个固定实例 `INSTANCE`。
>
> 这也就解释了**为什么枚举可以天然拿来实现单例**。
>
> 再往前一步，你刚刚问的“每个枚举常量拥有自己的方法实现”，实际上已经接触到了一个很有用的设计思想：**用枚举常量 + 多态，把不同分支的行为封装到枚举常量内部，从而减少大量 `if-else / switch`**

##### 枚举单例更偏向饿汉式

> > **枚举单例（Enum Singleton），利用枚举类初始化机制创建唯一实例。**
>
> 如果面试官非要让你在“懒汉 / 饿汉”二选一，我建议你回答：**更接近饿汉式**。
>
> ### 为什么？
>
> 你的代码：
>
> ```
> public enum Singleton_07 {
>     INSTANCE;
> }
> ```
>
> `INSTANCE` 是枚举常量，也就是一个对象。
>
> 当 `Singleton_07` **初始化时**，`INSTANCE` 就会被创建。
>
> 因此它不是：
>
> ```
> getInstance()
>     ↓
> 发现没有对象
>     ↓
> new 对象
> ```
>
> 这种“第一次调用获取方法时才创建”的典型懒汉式。
>
> 而更接近：
>
> ```
> Singleton_07 类初始化
>         ↓
> 创建 INSTANCE
>         ↓
> 之后访问 Singleton_07.INSTANCE
>         ↓
> 直接拿已经存在的对象
> ```
>
> 这和你前面的：
>
> ```
> public class Singleton_03 {
> 
>     private static final Singleton_03 instance =
>             new Singleton_03();
> 
>     private Singleton_03() {
>     }
> 
>     public static Singleton_03 getInstance() {
>         return instance;
>     }
> }
> ```
>
> 非常类似。
>
> 所以可以这样记：
>
> | 实现           | 分类                       |
> | -------------- | -------------------------- |
> | `Singleton_01` | 懒汉式                     |
> | `Singleton_02` | synchronized 懒汉式        |
> | `Singleton_03` | **饿汉式**                 |
> | `Singleton_04` | 静态内部类懒汉式           |
> | `Singleton_05` | DCL 懒汉式                 |
> | `Singleton_06` | CAS 懒汉式                 |
> | `Singleton_07` | **枚举单例，更接近饿汉式** |
>
> 不过有一个容易混淆的地方：
>
> **“类初始化时创建” ≠ “程序启动时就创建”。**
>
> Java 的类是**按需初始化**的。例如：
>
> ```
> public class Test {
>     public static void main(String[] args) {
> 
>         System.out.println("开始");
> 
>         // 第一次主动使用 Singleton_07
>         Singleton_07 s = Singleton_07.INSTANCE;
> 
>         System.out.println("结束");
>     }
> }
> ```
>
> 并不是 JVM 一启动，所有枚举类的 `INSTANCE` 都创建了。
>
> 而是：
>
> ```
> JVM 启动
>   ↓
> Test 初始化
>   ↓
> 执行 main()
>   ↓
> 第一次主动使用 Singleton_07
>   ↓
> 初始化 Singleton_07
>   ↓
> 创建 INSTANCE
> ```
>
> 所以最严谨的表述是：
>
> > **枚举单例依赖枚举类的初始化机制创建唯一实例。它不属于典型的懒汉式；如果按传统“懒汉/饿汉”分类，更接近饿汉式，但实际开发和面试中通常直接称为“枚举单例”更准确。**

> ### 1. 先看传统饿汉式
>
> 我们之前的：
>
> ```
> public class Singleton_03 {
> 
>     private static final Singleton_03 instance =
>             new Singleton_03();
> 
>     private Singleton_03() {
>     }
> 
>     public static Singleton_03 getInstance() {
>         return instance;
>     }
> }
> ```
>
> 这里的核心是：
>
> ```
> private static final Singleton_03 instance =
>         new Singleton_03();
> ```
>
> 当 `Singleton_03` **初始化时**，执行：
>
> ```
> new Singleton_03()
> ```
>
> 创建唯一对象。
>
> 所以它是：
>
> > **普通类 + static 成员变量 + private 构造方法**
>
> 利用 **Java 类初始化机制**实现饿汉式单例。
>
> ------
>
> ### 2. 再看枚举单例
>
> ```
> public enum Singleton_07 {
> 
>     INSTANCE;
> 
>     public void test() {
>         System.out.println("hi~");
>     }
> }
> ```
>
> 这里没有：
>
> ```
> new Singleton_07()
> ```
>
> 因为你根本不能自己 `new` 枚举对象。
>
> 实际上：
>
> ```
> Singleton_07.INSTANCE
> ```
>
> 中的 `INSTANCE` **本身就是唯一的那个 `Singleton_07` 对象**。
>
> 也就是说：
>
> ```
> Singleton_07 s1 = Singleton_07.INSTANCE;
> Singleton_07 s2 = Singleton_07.INSTANCE;
> 
> System.out.println(s1 == s2); // true
> ```
>
> ------
>
> ## 3. 两者最大的区别
>
> 可以这样理解：
>
> |              | 传统饿汉式                               | 枚举单例                 |
> | ------------ | ---------------------------------------- | ------------------------ |
> | 本质         | 普通 Java 类                             | `enum` 类型              |
> | 实例怎么产生 | `new Singleton_03()`                     | JVM 创建枚举常量         |
> | 构造方法     | 自己定义 `private`                       | 枚举构造器不能被外部调用 |
> | 唯一性       | 靠 `private constructor` + `static` 控制 | Java 枚举机制保证        |
> | 获取实例     | `getInstance()`                          | `Singleton_07.INSTANCE`  |
> | 线程安全     | 类初始化机制保证                         | 枚举初始化机制保证       |
> | 序列化       | 需要额外考虑                             | Java 对枚举有特殊保障    |
> | 反射攻击     | 理论上可以尝试破坏                       | 枚举有更强的语言级保护   |
>
> 所以**它们不是同一种实现，只是最终都能实现“一个实例”的效果。**
>
> ------
>
> ## 4. 为什么说枚举单例“更特殊”？
>
> 传统饿汉式本质上是：
>
> ```
> 普通类
>   ↓
> static instance
>   ↓
> new 一个对象
>   ↓
> 限制别人 new
>   ↓
> 实现单例
> ```
>
> 而枚举是 Java 语言层面专门提供的一种类型：
>
> ```
> enum Singleton_07
>         ↓
>     INSTANCE
>         ↓
> 这是一个真正的 Singleton_07 对象
>         ↓
> Java 保证这个枚举常量唯一
> ```
>
> 你甚至不能这样写：
>
> ```
> Singleton_07 s = new Singleton_07(); // ❌
> ```
>
> 也不能自己再创建第二个 `INSTANCE`。
>
> 所以枚举单例不是我们通过普通 Java 代码“设计”出来的唯一性，而是**借助 Java 枚举类型本身的语义获得唯一性**。
>
> ------
>
> ## 5. 还有一个非常重要的区别：初始化时机
>
> 这也是你前面问“饿汉还是懒汉”时最容易绕进去的地方。
>
> 传统饿汉：
>
> ```
> class Singleton_03 {
>     private static final Singleton_03 instance =
>         new Singleton_03();
> }
> ```
>
> **`Singleton_03` 类初始化时，就创建对象。**
>
> 而枚举：
>
> ```
> enum Singleton_07 {
>     INSTANCE;
> }
> ```
>
> 也是在 **`Singleton_07` 这个枚举类初始化时创建 `INSTANCE`**。
>
> 但注意：
>
> > **类初始化本身不是 JVM 启动时把所有类全部初始化。**
>
> 例如：
>
> ```
> public class Test {
>     public static void main(String[] args) {
> 
>         System.out.println("开始");
> 
>         // 第一次主动使用 Singleton_07
>         Singleton_07 s = Singleton_07.INSTANCE;
> 
>         System.out.println("结束");
>     }
> }
> ```
>
> 在执行：
>
> ```
> Singleton_07.INSTANCE
> ```
>
> 导致 `Singleton_07` 初始化时，才创建 `INSTANCE`。
>
> 因此从严格的 Java 语义来说：
>
> > **枚举单例不是“程序一启动就创建对象”。**
>
> 这也是为什么我前面说它**不能简单粗暴地等同于传统饿汉式**。
>
> ------
>
> ### 6. 你可以这样记
>
> 把这几个单例放在一起：
>
> ```
> Singleton_03
> 传统饿汉式
>         ↓
> 类初始化
>         ↓
> static instance = new Singleton_03()
> 
> 
> Singleton_04
> 静态内部类
>         ↓
> 第一次 getInstance()
>         ↓
> 初始化 Holder
>         ↓
> new Singleton_04()
> 
> 
> Singleton_05
> DCL
>         ↓
> 第一次 getInstance()
>         ↓
> synchronized + volatile
>         ↓
> new Singleton_05()
> 
> 
> Singleton_06
> CAS
>         ↓
> 第一次 getInstance()
>         ↓
> AtomicReference + CAS
>         ↓
> new Singleton_06()
> 
> 
> Singleton_07
> 枚举单例
>         ↓
> 枚举类初始化
>         ↓
> JVM 创建 INSTANCE
> ```
>
> 所以如果面试官问：
>
> > **“枚举单例是饿汉式还是懒汉式？”**
>
> 比较严谨的回答是：
>
> > **枚举单例通常单独作为一种实现方式来讨论，不严格归入传统的饿汉式或懒汉式。如果一定要二选一，它的实例是在枚举类初始化时创建，而不是第一次调用显式 getter 时创建，因此更接近饿汉式。但枚举类本身又遵循 Java 的按需初始化机制，所以不能理解成 JVM 启动时就创建。**
>
> 而**传统饿汉式和枚举单例真正的核心区别**不是“谁先创建”，而是：
>
> > **传统饿汉式依靠普通类的 `static` 字段 + `private` 构造方法实现单例；枚举单例依靠 Java `enum` 的语言级实例唯一性实现单例。**
