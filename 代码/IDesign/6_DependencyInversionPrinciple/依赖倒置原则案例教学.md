# 依赖倒置原则案例教学：抽奖策略

## 一、什么是依赖倒置原则？

依赖倒置原则（Dependency Inversion Principle，DIP）是 SOLID 原则之一，包含两层含义：

1. 高层模块不应该依赖低层模块，二者都应该依赖抽象；
2. 抽象不应该依赖细节，细节应该依赖抽象。

这里的“高层模块”是描述业务流程、表达业务意图的代码；“低层模块”是具体算法、数据库、消息中间件、第三方 SDK 等实现细节。DIP 不是让依赖凭空消失，而是把依赖方向从“业务依赖具体实现”调整为“业务与实现共同依赖稳定契约”。

通俗理解：业务代码只说“我要完成什么”，不要写死“必须用哪一种具体做法”；具体做法遵守业务定义的接口即可替换。

### 一个简单案例：通知服务

不使用 DIP 时，订单服务直接创建短信服务：

```java
class OrderService {
    void paid(Order order) {
        new SmsSender().send("订单已支付"); // 写死短信实现
    }
}
```

若要改为邮件、站内信或企业微信，`OrderService` 必须修改，业务流程与通知渠道紧耦合。

使用 DIP 后，订单服务依赖抽象：

```java
interface Notifier { void send(String message); }

class OrderService {
    private final Notifier notifier;
    OrderService(Notifier notifier) { this.notifier = notifier; }
    void paid(Order order) { notifier.send("订单已支付"); }
}

class SmsNotifier implements Notifier { /* 短信实现 */ }
class EmailNotifier implements Notifier { /* 邮件实现 */ }
```

`OrderService` 只依赖 `Notifier`；短信、邮件等细节反过来实现 `Notifier`。新增渠道时增加一个实现类即可，订单支付流程无需改变。

## 二、工程业务与代码结构

本工程模拟从参与抽奖的用户中选出中奖者。`BetUser` 有用户名和权重；工程提供两种抽奖算法：

- 随机抽奖：打乱列表后取前 N 名；
- 权重排名抽奖：按用户权重降序取前 N 名。

代码分成两组，用于对比：

| 区域 | 设计方式 | 核心代码 |
| --- | --- | --- |
| `com.ivanzhao.design.common` | 高层控制类直接包含具体算法 | `DrawControl.doDrawRandom`、`doDrawWeight` |
| `com.ivanzhao.design.DIP` | 通过抽象隔离抽奖算法 | `IDraw`、`DrawControl`、`DrawRandom`、`DrawWeightRank` |
| `src/test/.../common` | 调用反例 | `common.ApiTest` |
| `src/test/.../DIP` | 装配并调用正例 | `DIP.ApiTest` |

依赖关系对比如下：

```text
反例：
业务控制 DrawControl ──直接包含──► 随机算法细节 + 权重排序细节

正例：
                ┌── DrawRandom
                ├── DrawWeightRank
                ▼
业务控制 DrawControl ──依赖──► IDraw（抽奖契约）
```

## 三、哪里没有体现依赖倒置：`common` 包

`common/DrawControl.java` 同时实现了 `doDrawRandom` 和 `doDrawWeight`：

```java
public List<BetUser> doDrawRandom(List<BetUser> list, int count) { ... }
public List<BetUser> doDrawWeight(List<BetUser> list, int count) { ... }
```

该类一方面承担“发起抽奖”的高层业务意图，另一方面掌握 `Collections.shuffle`、权重排序和取前 N 名等具体算法细节。业务控制模块直接依赖具体实现，未通过抽象隔离，因此是本工程的 DIP 反例。

由此带来的问题包括：

- 新增“按签到次数抽奖”时需要修改 `DrawControl`；
- 替换或单独测试某个算法时，无法围绕统一契约替换实现；
- 控制流程与算法细节混在同一个类中，类会不断膨胀。

`common/ApiTest.java` 也只能调用 `doDrawRandom`、`doDrawWeight` 这类与具体策略绑定的方法，调用方的选择空间受限。

## 四、哪里体现依赖倒置：`DIP` 包

### 1. 用 `IDraw` 抽象描述稳定的业务能力

`DIP/IDraw.java` 定义了抽奖策略共同遵守的契约：

```java
public interface IDraw {
    List<BetUser> prize(List<BetUser> list, int count);
}
```

它只表达“从用户列表中选出指定数量中奖者”的能力，不暴露随机、排序等算法细节。对高层业务而言，这才是需要稳定依赖的抽象。

### 2. 具体算法依赖并实现抽象

`DrawRandom` 与 `DrawWeightRank` 都 `implements IDraw`：

```java
public class DrawRandom implements IDraw { ... }
public class DrawWeightRank implements IDraw { ... }
```

随机打乱、权重排序这些细节不再被 `DrawControl` 直接掌握，而是由实现类遵守 `IDraw` 契约。细节依赖抽象，符合 DIP 的第二层含义。

### 3. `DrawControl` 的方法参数依赖抽象

`DIP/DrawControl.java` 的核心方法是：

```java
public List<BetUser> doDraw(IDraw draw, List<BetUser> betUserList, int count) {
    return draw.prize(betUserList, count);
}
```

`DrawControl` 接收 `IDraw`，只调用抽象方法 `prize`，并不知道当前是随机抽奖还是权重抽奖。它可以在不修改自身的前提下支持任何新的 `IDraw` 实现，例如 `DrawCheckInRank`。

### 4. 测试展示了可替换策略

`DIP/ApiTest.java` 分别传入：

```java
drawControl.doDraw(new DrawRandom(), betUserList, 3);
drawControl.doDraw(new DrawWeightRank(), betUserList, 3);
```

同一个 `doDraw` 调用入口可以接受不同策略，这说明高层控制逻辑对算法实现具有可替换性。

## 五、案例中的边界与可改进点

### 1. 测试中 `new DrawRandom()` 是否违反 DIP？

通常不违反。系统必须在某个位置把抽象和具体实现装配起来，测试代码、`main` 方法、配置模块、Spring 容器配置等位置就是“组合根（Composition Root）”。在那里创建 `DrawRandom` / `DrawWeightRank` 是合理的；关键是业务类 `DrawControl` 没有自行 `new` 具体策略。

生产代码通常会使用构造器注入，使依赖更显式：

```java
class DrawControl {
    private final IDraw draw;
    DrawControl(IDraw draw) { this.draw = draw; }
    List<BetUser> doDraw(List<BetUser> users, int count) {
        return draw.prize(users, count);
    }
}
```

这也是依赖注入（DI）的一种形式。DI 是实现 DIP 的常见手段，但 DIP 是设计原则，DI 是把依赖传入对象的技术手段，两者不能等同。

### 2. 当前 `DrawControl` 的成员变量没有发挥作用

类中声明了 `private IDraw draw;`，但 `doDraw` 使用的是方法参数 `draw`，成员变量未初始化也未被使用。它不影响演示 DIP 的主线，却会造成误解。实际代码应二选一：删除无用成员变量，或使用构造器注入并由成员变量保存策略。

### 3. `BetUser` 并非 DIP 的核心

`BetUser` 是数据模型，直接被接口与实现使用在此场景合理。DIP 并不要求所有类都必须抽象化；应将抽象用在存在替换需求、变化频繁或需要隔离的依赖上。为每个简单数据类建立接口会增加无意义复杂度。

### 4. 算法会修改传入列表

`DrawRandom` 使用 `Collections.shuffle(list)`，`DrawWeightRank` 使用 `list.sort(...)`，都会改变调用方传入的原始列表。这是方法副作用和契约设计问题，而非 DIP 本身。若调用方需要保留原列表，应先复制列表再操作，并在 `IDraw` 的契约中明确这一行为。

### 5. 参数校验与边界条件

当 `count` 小于零或大于列表长度时，权重策略可能发生异常；随机策略在 `list.size() <= count` 时直接返回原列表。生产代码应统一校验输入、明确返回副本还是原对象，以及空列表的处理规则。抽象接口的语义越明确，具体策略就越容易安全替换。

## 六、面试提问、追问与参考回答

### 1. 什么是依赖倒置原则？

**回答：** 高层业务模块和低层实现细节都应该依赖抽象；抽象不依赖细节，细节实现抽象。这样业务流程不会绑定某一种数据库、消息渠道或算法，替换实现时影响更小。

**简单例子：** 订单服务依赖 `Notifier` 接口，而不是直接依赖 `SmsSender`。短信、邮件都实现 `Notifier`，切换通知渠道不需要修改订单支付流程。

**追问：它和“面向接口编程”有什么关系？**

**回答：** 面向接口编程是实践 DIP 的常见形式，但不能只看有没有接口。接口应由高层业务需要来定义，且高层实际依赖它；如果只是给具体类套一个无人使用的接口，或者接口本身依赖具体细节，就没有真正获得 DIP 的收益。

### 2. 本工程怎样体现 DIP？

**回答：** `IDraw` 定义抽奖契约；`DrawRandom`、`DrawWeightRank` 实现该契约；`DrawControl.doDraw` 的参数类型是 `IDraw`，只通过 `prize` 完成抽奖。控制类不需要了解随机或权重排序的实现细节。

**简单例子：** 给 `doDraw` 传入 `DrawRandom` 得到随机结果，传入 `DrawWeightRank` 得到按权重结果；`DrawControl` 的代码完全不变。

**追问：新增一种抽奖算法要改 `DrawControl` 吗？**

**回答：** 不需要。新增一个实现 `IDraw` 的类，例如 `DrawCheckInRank`，并在装配处传入即可。这同时有助于满足开闭原则。

### 3. `common.DrawControl` 为什么不符合 DIP？

**回答：** 它自己包含随机和权重排序算法，高层抽奖控制逻辑直接依赖低层算法细节。新增算法或修改某一算法都会修改这个控制类，变化没有被隔离。

**简单例子：** 要增加“按积分抽奖”，只能继续在 `DrawControl` 加 `doDrawScore`；而 DIP 方案只需新建 `DrawScoreRank implements IDraw`。

**追问：用 `if / else` 选择不同策略，算符合 DIP 吗？**

**回答：** 若业务类通过 `if / else` 创建并调用多个具体策略，它仍依赖那些实现，通常不符合 DIP。可以将选择逻辑集中在工厂、配置或依赖注入容器中，再让业务类只接收抽象。

### 4. DIP 与依赖注入（DI）有什么区别？

**回答：** DIP 是“应该依赖抽象”的设计原则；DI 是“由外部把依赖提供给对象”的实现方式。构造器注入、Setter 注入和方法参数注入都是 DI。DI 经常帮助实现 DIP，但即使用了 DI，如果注入的是具体类，仍未必符合 DIP。

**简单例子：** `new DrawControl(new DrawRandom())` 是构造器注入；`DrawControl` 字段声明为 `IDraw` 才体现它依赖抽象。

**追问：为什么通常推荐构造器注入？**

**回答：** 依赖在对象创建时就明确且不可缺失，字段可声明为 `final`，测试时也容易传入桩实现或模拟实现。可选依赖或运行期可变策略时，Setter/方法参数注入也有适用场景。

### 5. DIP 是否意味着所有类都要定义接口？

**回答：** 不意味着。应优先抽象变化点、外部依赖和需要替换或测试隔离的协作者。简单值对象、稳定的工具类或没有多态需求的内部实现，强行抽象往往只会增加层次。

**简单例子：** 本工程的 `BetUser` 只是用户数据对象，无需为它创建 `IBetUser`；抽奖算法有多种可替换实现，才适合抽象为 `IDraw`。

**追问：什么时候接口可以不必先建？**

**回答：** 当实现稳定、没有替换需求且尚无第二个调用场景时，可以从具体类开始，待明确出现变化点或测试隔离需求后再提取接口。设计应服务复杂度，而非为了形式堆抽象。

### 6. 如何测试 DIP 带来的收益？

**回答：** 让高层类只接收接口，在单元测试中传入一个可控的假实现（Fake）或 Mock，即可验证高层流程而无需运行真实算法、数据库或网络。

**简单例子：** 创建 `FixedDraw implements IDraw`，始终返回预设中奖名单；把它传给 `DrawControl`，即可稳定验证控制流程，不依赖随机结果。

**追问：Mock 太多是不是设计有问题？**

**回答：** 不一定。对外部系统或昂贵依赖使用 Mock 很正常；但如果为了测试一个简单业务不得不 Mock 很长的对象链，可能说明职责过多、依赖过深或抽象边界不合理，应回头审视设计。
